= Giới thiệu extension

SQL là một ngôn ngữ khai báo cho phép bạn tạo và thao tác với object cũng như dữ liệu. Bạn có thể nhóm các SQL statement thành script để thực thi theo cách dễ dự đoán và có thể tái lập hơn. Tuy nhiên, PostgreSQL coi các script như vậy là một sequence gồm những command không liên quan với nhau, nghĩa là bạn phải tự chịu trách nhiệm ghép các command đó thành những script phù hợp. Tình hình còn phức tạp hơn khi bạn phải xử lý các ngôn ngữ lập trình bên ngoài (ví dụ PL/Perl và những ngôn ngữ khác không dựa trên SQL) hoặc thư viện nhị phân; cluster không biết gì về mục đích của bạn hay mối quan hệ giữa các object. May mắn thay, extension giúp lập lại trật tự trong mớ hỗn độn này.

Extension là một tập hợp file được đóng gói, có thể được cài đặt vào cluster để cung cấp thêm chức năng, tức là mở rộng các tính năng hiện có của cluster. Không giống script, extension được quản lý chặt chẽ bằng các command cụ thể để cài đặt, triển khai, nạp và nâng cấp toàn bộ extension như một đơn vị thống nhất, ngay cả khi nó gồm nhiều file khác nhau.

Extension có thể phục vụ một mục đích tổng quát, chẳng hạn cung cấp data type mới, index type mới hoặc service gửi email trực tiếp từ bên trong PostgreSQL; cũng có thể rất cụ thể cho một trường hợp sử dụng nhất định, chẳng hạn một tập table và dữ liệu cung cấp ad hoc configuration. Extension không áp đặt cách bạn phải sử dụng nó, vì vậy bạn có thể tự do cài đặt rồi không dùng đến, hoặc dùng nó trong mọi database thuộc cluster.

Mục tiêu chính của cơ chế extension là cung cấp một interface chung để quản trị tính năng mới. Nhờ extension, bạn có một bộ statement thống nhất để triển khai, cài đặt, nâng cấp và gỡ bỏ extension như một đơn vị duy nhất trong cluster. Extension của bạn chỉ gồm một function hay cả một tập object liên kết với nhau cũng không quan trọng; cơ chế extension sẽ xử lý tất cả object cùng lúc, giúp việc quản trị dễ dàng hơn. Ngoài ra, hạ tầng extension còn định nghĩa một cách chuẩn để bổ sung tính năng theo cách có cấu trúc và gọn gàng, nhờ đó mọi người có thể đóng góp cho PostgreSQL dễ dàng hơn.

PostgreSQL đi kèm một tập hợp extension hữu ích trong gói `contrib`, do chính các nhà phát triển PostgreSQL phát triển. Vì vậy, các extension trong contrib ổn định và an toàn để sử dụng, vì chúng được tích hợp chặt chẽ với database PostgreSQL. Tuy nhiên, extension cũng có thể do bên thứ ba cung cấp, và đó chính là ưu điểm của cách tiếp cận này: bất kỳ ai cũng có thể đóng góp cho PostgreSQL bằng cách cung cấp tính năng mới thông qua extension. Lưu ý rằng các nhà phát triển PostgreSQL không bảo đảm tính ổn định của extension bên thứ ba.

[quote]
____
Các gói của hệ điều hành thường cung cấp gói `postgrsql-contrib`; gói này cài đặt toàn bộ extension contrib của PostgreSQL. Gói này được tách riêng để người dùng có thể chọn cài đặt các extension đó hay không. Rõ ràng, PostgreSQL vẫn hoạt động tốt ngay cả khi không có module `contrib`, vốn thực chất bổ sung tính năng thông qua extension.

____
PostgreSQL đã xây dựng cả một hệ sinh thái xoay quanh khái niệm extension. Vì vậy, PostgreSQL không chỉ cung cấp các statement để quản lý extension mà còn cung cấp một nền tảng để xây dựng extension mới và chuyển các script hiện có thành extension. Sau đó, extension có thể được cung cấp công khai thông qua một repository toàn cầu có tên *PostgreSQL eXtensions Network (PGXN)*.

Bạn có thể hình dung extension của PostgreSQL như các library có thể tái sử dụng trong một ngôn ngữ lập trình, chẳng hạn module của Perl, gem của Ruby, JAR của Java, v.v. Tương tự, hạ tầng PGXN có thể được xem là CPAN của Perl (hoặc PEAR của PHP, v.v.).

== Hệ sinh thái extension

Ưu điểm của extension là cung cấp một cách thống nhất để đóng gói các module có thể được triển khai (cài đặt) và sử dụng trong PostgreSQL. Nhà phát triển được tự do đóng góp, mở rộng số lượng module có sẵn cho PostgreSQL; tập hợp module này đã nhanh chóng phát triển thành một hệ sinh thái hoàn chỉnh như ngày nay.

Cũng như các ngôn ngữ lập trình như Perl, Python và những ngôn ngữ khác, PostgreSQL giờ đây có thể được tùy biến bằng các add-on và module dựa trên cùng một hạ tầng và kiến trúc, đồng thời được quản lý bằng cùng một bộ statement, bất kể chúng cung cấp chức năng gì.

Các extension chủ yếu được tập hợp trong PGXN, một repository trực tuyến có thể được truy vấn để lấy thông tin về extension hoặc tải xuống một extension (và một version cụ thể của extension đó), đồng thời có thể được cập nhật bằng các module mới.

[quote]
____
Hãy nhớ rằng PGXN đối với PostgreSQL cũng giống như CPAN đối với Perl, CTAN đối với LaTeX, PEAR đối với PHP, v.v.
____
Mặc dù có thể tìm thấy các extension PostgreSQL ở khắp nơi trên internet, nhiều khả năng bạn sẽ tương tác với PGXN gần như mỗi khi cần một extension mới. PGXN không chỉ là một website hay code repository đơn giản mà là một nền tảng hoàn chỉnh gồm bốn phần: search engine, extension manager, application programming interface (API) và client.

Search engine cho phép người dùng tìm kiếm một extension cụ thể trong nội dung của PGXN. Manager chịu trách nhiệm tiếp nhận các extension mới (hoặc version mới của extension) và cho phép người dùng lấy chúng (tức là phân phối extension). API định nghĩa cách ứng dụng tương tác với manager và search engine, qua đó định nghĩa cách xây dựng client. Có hai client chính: website PGXN và ứng dụng dòng lệnh `pgxnclient`. Ứng dụng dòng lệnh `pgxnclient` có lẽ là cách hiệu quả nhất để lấy và cài đặt extension; phần này sẽ được trình bày chi tiết trong các tiểu mục tiếp theo. Tuy nhiên, bạn cũng có thể tương tác trực tiếp với website PGXN để tìm kiếm và tải xuống extension. Ở phần sau của chương, bạn sẽ thấy một ví dụ sử dụng website PGXN.

Extension được xây dựng trên PostgreSQL eXtension System (PGXS), một bộ rule cơ bản mà extension phải tuân theo để cung cấp một interface quản lý thống nhất. Cụ thể, PostgreSQL cung cấp một Makefile thống nhất mà mọi extension nên sử dụng để cung cấp các chức năng chung phục vụ việc cài đặt, nâng cấp và gỡ bỏ extension. Bạn có thể kiểm tra Makefile cơ sở của PGXS bằng cách dùng `pg_config` để tìm vị trí của file này:

[source,console,role="transcript"]
....
$ pg_config --pgxs
/usr/lib/postgresql/16/lib/pgxs/src/makefiles/pgxs.mk
....

.Command
[source,bash]
....
pg_config --pgxs
....

.Output
[source,output]
....
/usr/lib/postgresql/16/lib/pgxs/src/makefiles/pgxs.mk
....


`pgxs.mk` là Makefile cơ sở cung cấp các chức năng chung cho mọi extension; cách sử dụng file này sẽ rõ ràng hơn khi chúng ta trình bày cách tạo extension từ đầu.

== Thành phần của extension

Một extension gồm hai thành phần chính: control file và script file:

* *Control file* cung cấp thông tin về extension và cách quản lý extension, chẳng hạn extension được cài đặt ở đâu, bằng cách nào và nâng cấp ra sao. Ở một mức độ nào đó, control file chính là metadata của extension.
* *Script file* là một file SQL chứa các statement để tạo những database object thuộc extension. Ở một mức độ nào đó, đây là nội dung của extension. Script file cũng có thể load các file khác để hoàn thiện extension, chẳng hạn shared library và các thành phần tương tự.

Khi bạn yêu cầu PostgreSQL cài đặt một extension, hệ thống sẽ kiểm tra control file để lấy thông tin về extension, bảo đảm extension chưa được cài đặt trước đó, rồi thực thi script file bên trong một transaction. Kết quả là extension sẽ sẵn sàng trong database của bạn.

Mỗi extension có một version để bạn có thể quyết định chính xác version nào cần cài đặt. Nếu không chỉ định version, PostgreSQL sẽ giả định rằng bạn muốn version mới nhất hiện có.

Extension được cài đặt trong share directory của cluster; bạn thường có thể tìm thấy thư mục này bằng cách chạy command `pg_config` với option `--sharedir`. Đây là một ví dụ:

[source,console,role="transcript"]
....
$ pg_config --sharedir
/usr/share/postgresql/16
....

.Command
[source,bash]
....
pg_config --sharedir
....

.Output
[source,output]
....
/usr/share/postgresql/16
....


Tất cả file tạo nên extension sẽ được đặt trong shared directory, và các file này phải có sẵn ở đó để user vận hành cluster (thường là user hệ điều hành `postgres`) có thể sử dụng. Khi các file đã có sẵn cho cluster, extension phải được cài đặt riêng trong từng database cần extension đó; hãy nhớ rằng PostgreSQL cung cấp isolation rất mạnh giữa các database, vì vậy extension được load vào database này sẽ không tự động có sẵn trong database khác. Tuy nhiên, hãy nhớ rằng template database (xem Chương 2) có thể được dùng làm khuôn mẫu cho các database mới tạo; vì vậy, sau khi bạn cài đặt một extension trong template database, extension đó sẽ có sẵn trong tất cả database khác được tạo ra.

== Control file

Một control file của extension phải có tên gắn với tên extension và có suffix `.control`. Ví dụ, `learnpg.control` là một tên hợp lệ.

Control file là một file văn bản trong đó bạn có thể chỉ định các directive, tức các chỉ dẫn và metadata để PostgreSQL xử lý việc cài đặt extension. Mỗi directive có một tên và một giá trị. Những directive phổ biến nhất gồm:

* `directory` chỉ định đường dẫn đến script của extension.
* `default_version` chỉ định version của extension sẽ được cài đặt khi người dùng không chỉ định version.
* `comment` là mô tả về extension và mục đích của nó.
* `requires` là danh sách tùy chọn gồm các extension khác cần thiết để cài đặt và sử dụng extension này, tức là một dependency list.
* `schema` chỉ định SQL schema nơi các extension object sẽ được cài đặt.
* `relocatable` cho biết extension có thể được chuyển sang một schema do người dùng chọn hay không.
* `superuser` cho biết extension có thể được cài đặt bởi các tài khoản không phải superuser hay không (mặc định là yes, nghĩa là chỉ superuser mới có thể cài đặt extension).

Mỗi extension phải có ít nhất một control file; file này được gọi là main control file. Tuy nhiên, một extension có thể có thêm các control file (gọi là secondary control file).

Mỗi secondary control file phải dành cho một version cụ thể và có cùng tên với main control file, trong đó version number được đặt sau tên extension và ngăn cách bằng double dash; ví dụ, nếu main control file là `learnpg.control`, các secondary control file có thể là `learnpg--1.1.control`, `learnpg--1.2.control`, v.v.

== Script file

Script file chứa SQL thuần để tạo các extension object. Một extension object có thể là table, trigger, function hoặc binding cho ngôn ngữ bên ngoài.

Mỗi script file phải được đặt tên theo tên extension và có suffix `.sql`; version của extension được chỉ định bằng một số đứng sau double dash. Ví dụ, file `learnpg--1.0.sql` tạo các object cho version 1.0 của extension.

Mỗi extension phải có ít nhất một script file nhưng có thể chỉ định nhiều file hơn. Trong trường hợp đó, mỗi file bổ sung phải ghi rõ version xuất phát và version đích cuối cùng của quá trình nâng cấp. Ví dụ, file `learnpg--1.0-1.1.sql` thực hiện nâng cấp từ version 1.0 lên version 1.1.

[quote]
____
Mỗi extension có một version number. Version number cao hơn biểu thị việc nâng cấp extension, còn version number thấp hơn biểu thị việc hạ cấp extension. Ví dụ, version 1.2 là bản nâng cấp của 1.1, còn 1.0 là bản hạ cấp.

____
Như đã nêu, script file được thực thi trong một transaction và vì vậy không thể tương tác với transaction boundary (nghĩa là không thể thực hiện `COMMIT` hoặc `ROLLBACK`). Tương tự, vì được thực thi trong một transaction, script file không được phép thực hiện bất kỳ thao tác nào không thể chạy trong transaction block (ví dụ các utility command như `VACUUM`).
