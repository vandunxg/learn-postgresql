= Khám phá disk layout của `PGDATA`

Trong các phần trước, bạn đã thấy cách cài đặt PostgreSQL và kết nối tới nó, nhưng chúng ta chưa xem xét storage của một database cluster. Vì PostgreSQL, cũng như mọi relational database, cần lưu trữ data lâu dài, cluster cần permanent storage. Cụ thể, PostgreSQL sử dụng filesystem bên dưới để lưu chính data của mình. Tất cả thành phần liên quan đến PostgreSQL đều nằm trong một directory có tên `PGDATA`.

Directory `PGDATA` đóng vai trò như một disk container, lưu trữ toàn bộ data của cluster, bao gồm user data và cluster configuration.

Sau đây là ví dụ về nội dung của `PGDATA` trong một PostgreSQL 16 cluster đang chạy:

[source,console,role="transcript"]
....
     $   ls -1 /postgres/16/data
     base
     global
     pg_commit_ts
     pg_dynshmem
     pg_hba.conf
     pg_ident.conf
     pg_logical
     pg_multixact
     pg_notify
     pg_replslot
     pg_serial
     pg_snapshots
     pg_stat
     pg_stat_tmp
     pg_subtrans
     pg_tblspc
     pg_twophase
     PG_VERSION
     pg_wal
     pg_xact
     postgresql.auto.conf
     postgresql.conf
     postmaster.opts
     postmaster.pid
....

.Command
[source,bash]
....

....

.Output
[source,output]
....

     global
     pg_commit_ts
     pg_dynshmem
     pg_hba.conf
     pg_ident.conf

`PGDATA` gồm nhiều file và subdirectory. Các file chính gồm:

* `postgresql.conf` là configuration file chính, được service sử dụng theo mặc định khi khởi động.
* `postgresql.auto.conf` là configuration file được tự động nạp, dùng để lưu các setting được thay đổi động bằng SQL statement.
* `pg_hba.conf` là HBA file chứa configuration liên quan đến các database connection có thể sử dụng.
* `PG_VERSION` là text file chứa major version number (hữu ích khi kiểm tra directory để xác định version của cluster đang sử dụng directory `PGDATA`).
* `postmaster.pid` là PID của postmaster process, tức process đầu tiên được khởi chạy của cluster.

Các directory chính trong `PGDATA` gồm:

* `base` là directory chứa toàn bộ user data, bao gồm các database, table và object khác.
* `global` là directory chứa các object dùng trên toàn cluster.
* `pg_wal` là directory chứa các WAL file.
* `pg_stat` và `pg_stat_tmp` lần lượt lưu thông tin thống kê lâu dài và tạm thời về trạng thái và hoạt động của cluster.

Tất nhiên, mọi file và directory trong `PGDATA` đều quan trọng để cluster hoạt động đúng. Tuy nhiên, hiện tại, danh sách trên chỉ liệt kê các object “core” tạo nên nền tảng của `PGDATA`. Các file và directory khác sẽ được thảo luận trong các chương sau.

== Các object trong directory `PGDATA`

PostgreSQL không đặt tên cho các object trên disk, chẳng hạn như table, bằng tên mnemonic hoặc tên dễ đọc; thay vào đó, mọi file đều được đặt tên bằng một numeric identifier. Bạn có thể thấy điều này khi xem subdirectory `base`, chẳng hạn:

[source,console,role="transcript"]
....
   $   ls -1 /postgres/16/data/base
   1
   16386
   4
   5
....

.Command
[source,bash]
....
  ls -1 /postgres/16/data/base
....

.Output
[source,output]
....
   1
   16386
   4
   5
....


Như bạn thấy trong output trên, directory `base` chứa bốn object có tên 1, 4, 5 và 16386. Lưu ý rằng các số này có thể khác trên máy của bạn. Cụ thể, mỗi object trong số đó là một directory chứa các file khác, như sau:

[source,console,role="transcript"]
....
      $ ls -1 /postgres/16/data/base/16386 | head
      112
      113
      1247
      1247_fsm
      1247_vm
      1249
      1249_fsm
      1249_vm
      1255
      1255_fsm
....

.Command
[source,bash]
....
ls -1 /postgres/16/data/base/16386 | head
....

.Output
[source,output]
....
      112
      113
      1247
      1247_fsm
      1247_vm
      1249
      1249_fsm
      1249_vm
      1255
      1255_fsm

Như bạn thấy, mỗi file được đặt tên bằng một numeric identifier. Bên trong, PostgreSQL lưu một catalog cụ thể cho phép database ánh xạ mnemonic name tới numeric identifier và ngược lại. Numeric identifier này được gọi là OID (hay Object Identifier); đây là một thuật ngữ mang tính lịch sử, ngày nay tương ứng với filenode. Hai thuật ngữ này sẽ được sử dụng thay thế cho nhau trong phần này.

Có một utility chuyên dụng cho phép bạn kiểm tra directory `PGDATA` và tra cứu tên mnemonic: `oid2name`. Ví dụ, nếu thực thi utility `oid2name`, bạn sẽ nhận được danh sách tất cả database hiện có, tương tự như sau:

[source,console,role="transcript"]
....
      $ oid2name
      All databases:
         Oid     Database Name   Tablespace
      ----------------------------------
       16390           forumdb   pg_default
             5        postgres   pg_default
             4       template0   pg_default
             1       template1   pg_default
....

.Command
[source,bash]
....
oid2name
....

.Output
[source,output]
....
      All databases:
         Oid     Database Name   Tablespace
      ----------------------------------
       16390           forumdb   pg_default
             5        postgres   pg_default
             4       template0   pg_default
             1       template1   pg_default
....


Như bạn thấy, các số OID trong output của `oid2name` tương ứng với tên của các directory được liệt kê trong directory `base`; mỗi subdirectory được đặt tên theo database tương ứng.

Bạn còn có thể kiểm tra một file đơn lẻ bằng cách vào directory của database và chỉ định database chứa object cần tra cứu bằng flag `-d`:

[source,console,role="transcript"]
....
   $ cd /postgres/16/data/base/1
   $ oid2name -d template1 -f 3395
   From database "template1":
      Filenode                       Table Name
   -------------------------------------
           3395   pg_init_privs_o_c_o_index
....

.Command
[source,bash]
....
cd /postgres/16/data/base/1
oid2name -d template1 -f 3395
....

.Output
[source,output]
....
   From database "template1":
      Filenode                       Table Name
   -------------------------------------
           3395   pg_init_privs_o_c_o_index
....


Như bạn thấy, file 3395 trong directory `/postgres/16/data/base/1` tương ứng với table có tên `pg_init_privs_o_c_o_index`. Vì vậy, khi PostgreSQL cần tương tác với một table như thế này, nó sẽ tìm file `/postgres/16/data/base/1/3395` trên disk.

Từ ví dụ trên, có thể thấy rõ rằng mọi SQL table đều được lưu trữ dưới dạng một file có tên là một số. Tuy nhiên, PostgreSQL không cho phép một file đơn lẻ lớn hơn 1 GB. Vậy điều gì xảy ra nếu một table tăng quá giới hạn đó? PostgreSQL tạo thêm một file có numeric extension cho biết chunk 1 GB tiếp theo. Nói cách khác, nếu table của bạn được lưu trong file `123`, gigabyte thứ hai sẽ được lưu trong file `123.1`, và nếu cần thêm một gigabyte storage nữa, file `123.2` sẽ được tạo. Vì vậy, filenode tham chiếu tới file đầu tiên liên quan đến một table cụ thể, nhưng trên disk có thể có nhiều file liên quan đến table đó.

== Tablespaces

PostgreSQL giả định rằng toàn bộ data của nó nằm trong directory `PGDATA`, nhưng điều đó không có nghĩa cluster của bạn bị “nhốt” trong directory này. Thực tế, PostgreSQL cho phép “thoát” khỏi directory `PGDATA` thông qua tablespace. Tablespace là một directory có thể nằm bên ngoài directory `PGDATA` và cũng có thể nằm trên một storage khác. Tablespace được ánh xạ vào directory `PGDATA` bằng các symbolic link được lưu trong subdirectory `pg_tblspc`. Nhờ vậy, PostgreSQL process không cần tìm kiếm bên ngoài `PGDATA` nhưng vẫn có thể truy cập storage bên ngoài. Tablespace có thể được dùng cho nhiều mục đích, chẳng hạn để mở rộng data storage hoặc cung cấp các mức hiệu năng storage khác nhau cho các object cụ thể. Ví dụ, bạn có thể tạo một tablespace trên storage chậm để chứa các object và table ít được truy cập, đồng thời dành storage nhanh trong một tablespace khác cho các object được truy cập thường xuyên.

Bạn không cần tự tạo link: PostgreSQL cung cấp tính năng `TABLESPACE` để quản lý việc này, và cluster sẽ tạo cũng như quản lý các link phù hợp trong subdirectory `pg_tblspc`.

Ví dụ, sau đây là một directory `PGDATA` có ba tablespace khác nhau:

[source,console,role="transcript"]
....
     $ ls -l /postgres/16/data/pg_tblspc/
     lrwxrwxrwx 1 postgres postgres 22 Jan 19 13:08 16384 -> /data/tablespaces/
     ts_a
     lrwxrwxrwx 1 postgres postgres 22 Jan 19 13:08 16385 -> /data/tablespaces/
     ts_b
     lrwxrwxrwx 1 postgres postgres 22 Jan 19 13:08 16386 -> /data/tablespaces/
     ts_c
....

.Command
[source,bash]
....
ls -l /postgres/16/data/pg_tblspc/
....

.Output
[source,output]
....
     lrwxrwxrwx 1 postgres postgres 22 Jan 19 13:08 16384 -> /data/tablespaces/
     ts_a
     lrwxrwxrwx 1 postgres postgres 22 Jan 19 13:08 16385 -> /data/tablespaces/
     ts_b
     lrwxrwxrwx 1 postgres postgres 22 Jan 19 13:08 16386 -> /data/tablespaces/
     ts_c
....


Như bạn thấy trong ví dụ trên, có ba tablespace được gắn với storage `/data`. Bạn có thể kiểm tra chúng bằng `oid2name` với flag `-s`:

[source,console,role="transcript"]
....
      $ oid2name -s
      All tablespaces:
            Oid   Tablespace Name
      ------------------------
           1663        pg_default
           1664         pg_global
          16384               ts_a
          16385               ts_b
          16386               ts_c
....

.Command
[source,bash]
....
oid2name -s
....

.Output
[source,output]
....
      All tablespaces:
            Oid   Tablespace Name
      ------------------------
           1663        pg_default
           1664         pg_global
          16384               ts_a
          16385               ts_b
          16386               ts_c
....


Như bạn thấy, các numeric identifier của symbolic link được ánh xạ tới mnemonic name của tablespace. Ví dụ trên cũng cho thấy có hai tablespace đặc biệt:

* `pg_default` là default tablespace tương ứng với “none”, tức là storage mặc định được dùng cho mọi object khi không có gì được chỉ định rõ ràng. Nói cách khác, mọi object được lưu trực tiếp trong directory `PGDATA` đều được gắn với tablespace `pg_default`.
* `pg_global` là tablespace được dùng cho các system-wide object.

Theo mặc định, cả hai tablespace trên đều trỏ trực tiếp tới directory `PGDATA`, nghĩa là mọi cluster không có tablespace tùy chỉnh đều nằm hoàn toàn bên trong directory `PGDATA`.
