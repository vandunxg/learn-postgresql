= Câu lệnh EXPLAIN

`EXPLAIN` là statement cho phép bạn xem PostgreSQL sẽ thực thi một query cụ thể ra sao. Bạn truyền statement cần phân tích cho `EXPLAIN`, rồi execution plan sẽ được hiển thị.

Có một vài điều quan trọng cần biết trước khi dùng `EXPLAIN`:

* Nó chỉ hiển thị plan tốt nhất, tức plan có cost thấp nhất trong số tất cả các plan đã được đánh giá.
* Nó không thực thi statement mà bạn yêu cầu lập plan, trừ khi bạn yêu cầu thực thi statement đó một cách rõ ràng. Vì vậy, chạy `EXPLAIN` thường nhanh và gần như không thay đổi giữa các lần chạy.
* Nó trình bày tất cả execution node mà executor sẽ dùng để tạo ra dataset.

Hãy xem một ví dụ về `EXPLAIN` để hiểu rõ hơn. Giả sử chúng ta cần hiểu execution plan của statement `SELECT * FROM categories`. Khi đó, đặt command `EXPLAIN` trước statement như sau:

[source,console,role="transcript"]
....
   forumdb=> EXPLAIN SELECT * FROM categories;
                                QUERY PLAN
   -----------------------------------------------------------
   Seq Scan on categories        (cost=0.00..1.05 rows=5 width=68)
   (1 row)
....

.SQL
[source,sql]
....
EXPLAIN SELECT *
FROM categories;
....

.Output
[source,output]
....
                                QUERY PLAN
   -----------------------------------------------------------
   Seq Scan on categories        (cost=0.00..1.05 rows=5 width=68)
   (1 row)
....


Như bạn có thể thấy, output của `EXPLAIN` báo cáo query plan. Plan chỉ có một execution node, thuộc loại `Seq Scan`, sau đó là table nơi node được thực thi (`categories`). Trong output của command `EXPLAIN`, bạn sẽ thấy tất cả loại execution node đã được thảo luận ở các phần trước.

Với mỗi node, `EXPLAIN` cũng báo cáo một số thông tin trong dấu ngoặc: cost, số row và width. Cost là mức công việc cần thiết để thực thi node, và luôn được biểu diễn dưới dạng “startup cost” và “final cost”. Startup cost là lượng công việc PostgreSQL phải thực hiện trước khi bắt đầu thực thi node; trong ví dụ trên, cost bằng 0, nghĩa là node có thể bắt đầu thực thi ngay lập tức. Final cost là mức công việc PostgreSQL phải thực hiện để cung cấp phần cuối của dataset, tức là hoàn tất việc thực thi node.

Field `rows` cho biết node được kỳ vọng sẽ cung cấp bao nhiêu tuple trong dataset cuối cùng; đây hoàn toàn chỉ là một ước tính. Vì là ước tính, giá trị này có thể sai. Bạn cũng cần nhớ rằng nó sẽ không bao giờ bằng zero: khi PostgreSQL ước tính số tuple rất thấp, nó luôn dùng 1 làm số row.

Cuối cùng, field `width` cho biết trung bình mỗi tuple chiếm bao nhiêu bit. Về cơ bản, thông tin này được dùng để ước tính network traffic mà query sẽ tạo ra: trong ví dụ trên, có thể ước tính 68 byte cho mỗi tuple.

Bây giờ hãy xem một ví dụ khác để làm quen với output của `EXPLAIN`. Query chỉ thay đổi một chút để tạo thêm một vài node, như sau:

[source,console,role="transcript"]
....
      forumdb=> EXPLAIN
                 SELECT title
                 FROM categories ORDER BY description DESC;
                                 QUERY PLAN                                           ---------
      --------------------------------------------------------
      Sort   (cost=1.11..1.12 rows=5 width=64)
        Sort Key: description DESC
        ->   Seq Scan on categories      (cost=0.00..1.05 rows=5 width=64)
....

.SQL
[source,sql]
....
EXPLAIN SELECT title
FROM categories
ORDER BY description DESC;
....

.Output
[source,output]
....
                                 QUERY PLAN                                           ---------
      --------------------------------------------------------
      Sort   (cost=1.11..1.12 rows=5 width=64)
        Sort Key: description DESC
        ->   Seq Scan on categories      (cost=0.00..1.05 rows=5 width=64)
....


Ở đây có hai node khác nhau: node đầu tiên ở trên cùng là node `Sort` (do clause `ORDER BY`), còn node thứ hai là `Seq Scan`, giống như trong ví dụ trước. Lưu ý rằng output có ba dòng; vậy làm thế nào để xác định dòng nào là node và dòng nào không phải? Dòng đầu tiên trong plan luôn là một node, còn các dòng node khác được thụt vào bên phải và có mũi tên làm tiền tố (`->`). Các dòng còn lại trong plan cung cấp thông tin về node mà chúng trực thuộc; vì vậy, trong ví dụ trên, dòng `Sort Key` là thông tin bổ sung cho node `Sort`.

Một cách khác để phân biệt dòng node với thông tin bổ sung là nhận ra rằng mọi dòng node đều có các thuộc tính cost, rows và width trong dấu ngoặc.

Sau khi xác định các node của query, bạn cần tìm node đầu tiên. Đây thường là node được thụt vào nhiều nhất và cũng là node có startup cost thấp nhất; trong ví dụ trên, `Seq Scan` là node được thực thi đầu tiên. Node này thực hiện đúng điều đã mô tả trong ví dụ trước: buộc executor truy cập table trên storage vật lý và lấy toàn bộ data của table theo thứ tự tuần tự. Tuy nhiên, có một điểm khác so với ví dụ trước: width trung bình đã giảm vì query không yêu cầu tất cả column của mọi tuple mà chỉ yêu cầu column `title`.

Khi node `Sequential Scan` hoàn tất, output của nó được dùng làm input cho node `Sort`, node thực hiện operation `ORDER BY` mong muốn. Như có thể thấy, sort key của statement ban đầu được in ra để cung cấp đủ thông tin giúp bạn hiểu executor sẽ sort data theo tiêu chí nào. Node `Sort` có startup cost lớn hơn (hoặc gần như bằng) final cost của node trước: sequential scan có final cost là 1.05, còn sort bắt đầu với cost 1.11. Điều này một lần nữa nhấn mạnh rằng các node được thực thi theo pipeline, đồng thời cho biết sort không thể bắt đầu trước khi node kia hoàn tất. Node `Sort` có final cost gần bằng startup cost, nghĩa là PostgreSQL thực hiện node này khá đơn giản.

Bạn có thể thử chạy `EXPLAIN` trên các statement khác nhau để xem plan thay đổi ra sao và những node nào có thể được tạo ra, từ đó học cách nhận biết node và thông tin tài nguyên.

Trong các phần sau, bạn sẽ thấy những option khác nhau để phân tích một statement.

== Các format output của EXPLAIN

Mặc định, `EXPLAIN` cung cấp output dạng text, nhưng cũng có thể cung cấp output có cấu trúc hơn nhiều dưới dạng XML, JSON và YAML. Các format này không chỉ hữu ích khi bạn làm việc với tool và application bên ngoài, mà còn hữu ích vì chúng cung cấp thêm thông tin để tuning query plan.

Bạn có thể chỉ định format mong muốn bằng option `FORMAT`, theo sau là tên format: `TEXT`, `XML`, `JSON` hoặc `YAML`. Hãy xem ví dụ sau:

[source,console,role="transcript"]
....
   forumdb=> EXPLAIN ( FORMAT JSON ) SELECT * FROM categories;
                       QUERY PLAN
   --------------------------------------
    [                                           +
       {                                       +
           "Plan": {                           +
               "Node Type": "Seq Scan",        +
               "Parallel Aware": false,        +
               "Async Capable": false,         +
               "Relation Name": "categories",+
               "Alias": "categories",          +
               "Startup Cost": 0.00,             +
               "Total Cost": 1.05,             +
               "Plan Rows": 5,                 +
               "Plan Width": 68                +
           }                                   +
       }                                       +
   ]


   (1 row)
....

.SQL
[source,sql]
....
EXPLAIN (FORMAT JSON) SELECT * FROM categories;
....

.Output
[source,output]
....
                       QUERY PLAN
   --------------------------------------
    [                                           +
       {                                       +
           "Plan": {                           +
               "Node Type": "Seq Scan",        +
               "Parallel Aware": false,        +
               "Async Capable": false,         +
               "Relation Name": "categories",+
               "Alias": "categories",          +
               "Startup Cost": 0.00,             +
               "Total Cost": 1.05,             +
               "Plan Rows": 5,                 +
               "Plan Width": 68                +
           }                                   +
       }                                       +
   ]


   (1 row)
....


Như bạn có thể thấy, format JSON không chỉ cung cấp một cấu trúc khác cho query plan mà còn cung cấp một tập thông tin khác và phong phú hơn. Chẳng hạn, từ ví dụ trên có thể thấy query đã được thực thi ở chế độ nonparallel (`"Parallel Aware": false,`).

Nếu cần parse output của `EXPLAIN` bằng application hoặc tool, bạn nên dùng một trong các format có cấu trúc thay vì format text mặc định.

== EXPLAIN ANALYZE

Mode `ANALYZE` của `EXPLAIN` mở rộng command bằng cách thực sự thực thi query cần phân tích. Vì vậy, command này thực hiện hai nhiệm vụ: in ra plan tốt nhất để thực thi query, đồng thời thực thi query và báo cáo một số thông tin thống kê.

Để hiểu rõ hơn khái niệm này, hãy so sánh output của `EXPLAIN ANALYZE` với output của command `EXPLAIN` thông thường:

[source,console,role="transcript"]
....
      forumdb=> EXPLAIN SELECT * FROM posts;
                               QUERY PLAN
      ----------------------------------------------------------
      Seq Scan on posts   (cost=0.00..31.04 rows=1004 width=71)
      (1 row)




      forumdb=> EXPLAIN ANALYZE SELECT * FROM posts;
                                                           QUERY PLAN
      --------------------------------------------------------------------------
      -----------------------------
      Seq Scan on posts (cost=0.00..31.04 rows=1004 width=71) (actual
      time=0.006..0.101 rows=1004 loops=1)
      Planning Time: 0.052 ms
      Execution Time: 0.163 ms
      (3 rows)
....

.SQL
[source,sql]
....
EXPLAIN SELECT *
FROM posts;
EXPLAIN ANALYZE SELECT * FROM posts;
....

.Output
[source,output]
....
                               QUERY PLAN
      ----------------------------------------------------------
      Seq Scan on posts   (cost=0.00..31.04 rows=1004 width=71)
      (1 row)




                                                           QUERY PLAN
      --------------------------------------------------------------------------
      -----------------------------
      Seq Scan on posts (cost=0.00..31.04 rows=1004 width=71) (actual
      time=0.006..0.101 rows=1004 loops=1)
      Planning Time: 0.052 ms
      Execution Time: 0.163 ms
      (3 rows)
....


Output của command `EXPLAIN ANALYZE` được bổ sung phần "actual" cho mỗi node: executor báo cáo chính xác node đã được thực thi như thế nào. Vì vậy, trong khi `EXPLAIN` chỉ có thể ước tính cost của node, `EXPLAIN ANALYZE` cung cấp execution time (tính bằng millisecond), số row thực tế và số lần node được thực thi (loops).

Thời gian của node được biểu diễn, tương tự cost, bằng startup time và final time; final time là thời gian cần để node hoàn tất việc thực thi. Vì vậy, trong ví dụ trên, PostgreSQL mất 0.006 millisecond để "warm up" và hoàn tất việc thực thi query trong 0.101 millisecond, nên node cần 0.107 millisecond để hoàn thành công việc.

Một phần thông tin quan trọng khác trong phần actual của output node là số row, tức node đã tạo ra bao nhiêu tuple, tương tự như ước tính của `EXPLAIN` thông thường. Tại sao cần báo cáo số row mà node thu được? Hãy nhớ rằng `EXPLAIN` đưa ra ước tính, còn `EXPLAIN ANALYZE` cung cấp số tuple thực tế mà node thu được. Khi hai giá trị này thực sự khác nhau từ một bậc độ lớn trở lên, PostgreSQL không thể ước tính chính xác kích thước result set và do đó không thể chọn plan tốt nhất để truy cập data; nghĩa là nó có thể chọn một access method không tối ưu.

Cuối cùng, output actual có số loop, tức số lần chính node đó đã được thực thi. Thông thường số này là 1, nghĩa là node chỉ được thực thi một lần, nhưng nếu node thuộc về một subquery thì giá trị có thể lớn hơn 1. Timing và số row liên quan đến một lần thực thi loop; do đó, để có các giá trị cuối cùng, bạn cần nhân rows và time với loops.

Ở cuối output của command, `EXPLAIN ANALYZE` cung cấp thông tin thời gian tổng thể, bao gồm planning time, tức thời gian optimizer đã dùng để tạo access plan tốt nhất, và execution time, tức tổng thời gian đã dùng để chạy query (không bao gồm parsing và planning time).

Vì vậy, ví dụ trên mất 0.163 millisecond để lấy data và 0.052 millisecond để quyết định cách lấy data. Tổng thời gian của query là 0.219 millisecond, nhỉnh hơn một chút so với 0.052 + 0.163 vì một phần thời gian được dùng để cấp phát tài nguyên.

[quote]
____
Khi lượng data cần truy cập rất nhỏ, planning time sẽ dài hơn execution time.

____
Execution time cũng bao gồm thời gian chạy các trigger `BEFORE`, còn trigger `AFTER` không được tính vì function của chúng được thực thi sau khi plan đã hoàn tất.

Tương tự, planning time chỉ tính thời gian dùng để tạo access plan tốt nhất; không tính thời gian cần để xử lý rule và viết statement, cũng như parsing.

[quote]
____
`EXPLAIN ANALYZE` luôn thực thi query mà bạn muốn phân tích. Do đó, để tránh side effect, bạn nên bọc `EXPLAIN ANALYZE` trong một transaction và rollback công việc sau khi hoàn tất phân tích.

____
Bạn cũng có thể gọi `EXPLAIN ANALYZE` bằng cách truyền `ANALYZE` làm option cho `EXPLAIN`, như sau:

[source,console,role="transcript"]
....
      forumdb=> EXPLAIN ( ANALYZE ) SELECT * FROM categories ORDER BY title
      DESC;
....

.SQL
[source,sql]
....
EXPLAIN (ANALYZE) SELECT * FROM categories ORDER BY title
    DESC;
....


Dạng option của `EXPLAIN ANALYZE` tiện dụng khi bạn muốn thêm các option khác cho `EXPLAIN`, như sẽ trình bày trong phần sau.

== Các option của EXPLAIN

`EXPLAIN` cung cấp một tập option phong phú, phần lớn trong số đó chỉ có thể dùng ở dạng `ANALYZE`. Tất cả option của `EXPLAIN` được trình bày trong phần này đều là boolean, nghĩa là chúng chỉ có thể được bật hoặc tắt.

Option `VERBOSE` cho phép mỗi node báo cáo thông tin chi tiết hơn, chẳng hạn danh sách output column, kể cả khi query không chỉ định rõ danh sách đó. Ví dụ, dù query không yêu cầu rõ ràng danh sách column, `VERBOSE` vẫn cho biết node sẽ cung cấp những column nào cho output dataset:

[source,console,role="transcript"]
....
      forumdb=> EXPLAIN (VERBOSE on) SELECT * FROM categories;
                                    QUERY PLAN
      -----------------------------------------------------------------
      Seq Scan on forum.categories       (cost=0.00..1.05 rows=5 width=68)
        Output: pk, title, description
      (2 rows)
....

.SQL
[source,sql]
....
EXPLAIN (VERBOSE ON) SELECT * FROM categories;
....

.Output
[source,output]
....
                                    QUERY PLAN
      -----------------------------------------------------------------
      Seq Scan on forum.categories       (cost=0.00..1.05 rows=5 width=68)
        Output: pk, title, description
      (2 rows)
....


Option `SETTINGS` được dùng để xác định query có được plan bằng một configuration khác với bộ configuration chung ở cấp cluster hay không. Một số thay đổi có thể được áp dụng ở cấp session; do đó, `EXPLAIN` có thể báo cáo session có đang dùng custom setting hay không. Ví dụ, hãy xét việc thay đổi parameter `work_mem`. Dù parameter này không liên quan đến query trong ví dụ sau, `EXPLAIN` vẫn báo cáo nó vì đây là parameter đã được thay đổi thủ công trước khi query được plan:

[source,console,role="transcript"]
....
      forumdb=> SHOW work_mem;
      work_mem
      ----------
      4MB
      (1 row)
....

.SQL
[source,sql]
....
SHOW work_mem;
....

.Output
[source,output]
....
      work_mem
      ----------
      4MB
      (1 row)
....


[source,console,role="transcript"]
....
   forumdb=> SET work_mem TO '32MB';
   SET
   forumdb=> EXPLAIN (SETTINGS on) SELECT * FROM posts ORDER BY created_on
   DESC;
                                     QUERY PLAN
   ----------------------------------------------------------------------
   Sort      (cost=164403.31..166903.32 rows=1000004 width=75)
      Sort Key: created_on DESC
      ->     Seq Scan on posts   (cost=0.00..20309.04 rows=1000004 width=75)
   Settings: work_mem = '32MB'
   (4 rows)
....

.SQL
[source,sql]
....
SET work_mem TO '32MB';
EXPLAIN (SETTINGS ON) SELECT * FROM posts ORDER BY created_on
   DESC;
....

.Output
[source,output]
....
   SET
                                     QUERY PLAN
   ----------------------------------------------------------------------
   Sort      (cost=164403.31..166903.32 rows=1000004 width=75)
      Sort Key: created_on DESC
      ->     Seq Scan on posts   (cost=0.00..20309.04 rows=1000004 width=75)
   Settings: work_mem = '32MB'
   (4 rows)
....


Nhờ option `SETTINGS`, bạn có thể biết query plan có được tạo với custom configuration của một số parameter hay không, từ đó hiểu rõ hơn liệu các parameter đó có ảnh hưởng đến query plan hay không.

Option `COSTS`, được bật theo mặc định, hiển thị phần cost của một node. Ví dụ, tắt option này sẽ loại bỏ startup cost và final cost, cùng với width trung bình và số row:

[source,console,role="transcript"]
....
   forumdb=> EXPLAIN (COSTS off) SELECT * FROM categories;
              QUERY PLAN
   ------------------------
    Seq Scan on categories
   (1 row)


   forumdb=> EXPLAIN (COSTS on) SELECT * FROM categories;
                           QUERY PLAN
   -----------------------------------------------------------
    Seq Scan on categories       (cost=0.00..1.05 rows=5 width=68)



   (1 row
....

.SQL
[source,sql]
....
EXPLAIN (COSTS off) SELECT * FROM categories;
EXPLAIN (COSTS ON) SELECT * FROM categories;
....

.Output
[source,output]
....
              QUERY PLAN
   ------------------------
    Seq Scan on categories
   (1 row)


                           QUERY PLAN
   -----------------------------------------------------------
    Seq Scan on categories       (cost=0.00..1.05 rows=5 width=68)



   (1 row
....


Option `TIMING`, được bật theo mặc định, hiển thị execution time thực tế khi `EXPLAIN` được gọi với `ANALYZE`. Nói cách khác, đặt `TIMING` thành off có nghĩa là output của `EXPLAIN` sẽ không hiển thị thời gian thực thi node.
Ví dụ, trong statement `EXPLAIN` sau đây, actual time không xuất hiện trong output:

[source,console,role="transcript"]
....
forumdb=> EXPLAIN (ANALYZE on, TIMING off) SELECT * FROM categories;
                                  QUERY PLAN
--------------------------------------------------------------------------
---------
Seq Scan on categories      (cost=0.00..1.05 rows=5 width=68) (actual rows=5
loops=1)
Planning Time: 0.113 ms
Execution Time: 0.047 ms
(3 rows)
....

.SQL
[source,sql]
....
EXPLAIN (ANALYZE ON, TIMING off) SELECT * FROM categories;
....

.Output
[source,output]
....
                                  QUERY PLAN
--------------------------------------------------------------------------
---------
Seq Scan on categories      (cost=0.00..1.05 rows=5 width=68) (actual rows=5
loops=1)
Planning Time: 0.113 ms
Execution Time: 0.047 ms
(3 rows)
....


Option `SUMMARY` báo cáo tổng planning time và execution time của query, nhờ đó bạn có thể hình dung query planner cần bao nhiêu công sức để tìm ra execution plan tốt nhất.

Option `BUFFERS`, mặc định là off, cung cấp thông tin về các data buffer mà query đã sử dụng để hoàn tất. Ví dụ, hãy lưu ý thông tin về buffer của execution node trong query sau:

[source,console,role="transcript"]
....
forumdb=> EXPLAIN (ANALYZE, BUFFERS on) SELECT * FROM posts;
                                                             QUERY PLAN
--------------------------------------------------------------------------
-----------------------------
Seq Scan on posts (cost=0.00..31.04 rows=1004 width=71) (actual
time=0.006..0.100 rows=1004 loops=1)
  Buffers: shared hit=21
Planning Time: 0.061 ms
Execution Time: 0.171 ms
(4 rows)
....

.SQL
[source,sql]
....
EXPLAIN (ANALYZE, BUFFERS ON) SELECT * FROM posts;
....

.Output
[source,output]

Thông tin về buffer không đơn giản để phân tích và có thể chia thành hai phần: prefix và suffix.

Prefix có thể có một trong các giá trị sau:

* `shared`, nghĩa là PostgreSQL shared buffer, tức cache trong memory của database
* `temp`, nghĩa là temporary memory (được dùng cho sorting, hashing, v.v.)
* `local`, nghĩa là không gian dành cho các temporary database object (ví dụ, temporary tables)

Suffix có thể có một trong các giá trị sau:

* `hit`, cho biết số lần memory access thành công
* `read`, cho biết số buffer được đọc từ storage (vì vậy không nằm trong cache)
* `dirtied`, cho biết số buffer đã được query sửa đổi
* `written`, cho biết số buffer bị loại khỏi PostgreSQL cache và được ghi xuống disk
* `lossy`, cho biết số buffer PostgreSQL đã kiểm tra trong memory ở pass thứ hai

Kết hợp prefix và suffix sẽ cung cấp thông tin về các buffer. Ví dụ, trong query trên, dòng buffer chứa `shared hit=21` có nghĩa là "21 buffer đã được tìm thấy thành công trong database cache, không cần thực hiện thêm operation nào trên buffer."

Kích thước WAL sẽ luôn lớn hơn kích thước thực tế của table. Ví dụ, trong ví dụ trên, data được tạo trong table có kích thước khoảng 13 MB, trong khi WAL lớn hơn nhiều, khoảng 46 MB. Lý do của chênh lệch này là PostgreSQL phải bảo đảm data an toàn trong WAL và hữu ích cho crash recovery. Vì vậy, WAL không chỉ lưu content của data mà còn lưu metadata về cách restore content đó một cách chính xác.
