= Khám phá physical backup

Physical backup là loại backup low-level được thực hiện khi database cluster vẫn đang hoạt động bình thường. Ở đây, low-level có nghĩa là backup được thực hiện theo một cách nào đó “bên ngoài” cluster đang được backup, cụ thể là ở filesystem level.

Như đã biết ở Chương 10, Users, Roles và Database Security, database cluster cần các data file trong `PGDATA/base` và WAL trong `PGDATA/wal`, cùng một số file khác, để cluster hoạt động đúng. Điểm mấu chốt là các data file và WAL cho phép cluster tự phục hồi sau crash. Vì vậy, physical backup sao chép toàn bộ file của cluster; khi cần restore, nó mô phỏng một database crash rồi để cluster tự phục hồi bằng WAL sẵn có.

Physical backup quan trọng vì cho phép chúng ta clone một cluster một cách hiệu quả, bắt đầu từ các file cấu thành cluster đó. Điều này có nghĩa là, một mặt, bạn không thể restore một cluster đã được physical backup với một PostgreSQL version khác; mặt khác, trong giai đoạn backup, về cơ bản bạn không cần tương tác với cluster.

Điểm sau đặc biệt quan trọng: physical backup có thể được thực hiện hầu như bất kỳ lúc nào mà không tác động đến database bằng một transaction lớn như logical backup, cũng không can thiệp vào các activity đang diễn ra của database, chẳng hạn như client connection và query. Đúng là storage system, đặc biệt là filesystem, sẽ chịu tải trong kiểu backup này, nhưng với cluster thì backup gần như trong suốt.

Có thể nói, cluster phải được thông báo khi backup bắt đầu để ghi nhận trong WAL rằng backup đang diễn ra; nhưng ngoài hành động “đơn giản” này, backup hoàn toàn nằm ngoài database cluster.

Hơn nữa, physical backup cho phép bạn chọn tool phù hợp nhất cho việc low-level file copy. Bạn có thể tự do sử dụng bất kỳ filesystem-specific command nào, chẳng hạn `cp(1)`, `rsync(1)`, `tar(1)`, v.v.; bạn có thể thực hiện backup qua network bằng bất kỳ cơ chế copy file nào do operating system cung cấp, thậm chí còn có thể tự phát triển tool riêng. PostgreSQL cũng có rất nhiều backup solution, trong đó tool được các tác giả yêu thích là `pgBackRest`, nên bạn có thể tùy chỉnh backup strategy bằng những tool phù hợp nhất với môi trường và yêu cầu của mình.

Ở các subsection tiếp theo, bạn sẽ học cách thực hiện physical backup bằng tool đi kèm PostgreSQL là `pg_basebackup`. Tool này được phát triển chủ yếu để clone một cluster, chẳng hạn làm điểm bắt đầu cho một replicated system (replication sẽ được trình bày ở các chương sau).

Cần lưu ý rằng, về bản chất, những gì `pg_basebackup` thực hiện trong mọi trường hợp chỉ là một tập hợp các bước mà bất kỳ system administrator nào cũng có thể thực hiện thủ công; vì vậy, tool này cung cấp một cách thuận tiện và đã được kiểm chứng kỹ lưỡng để thực hiện physical backup.

== Thực hiện physical backup thủ công

Tool `pg_basebackup` thực hiện việc clone một database cluster local hoặc remote để có thể dùng làm backup. Để hoạt động đúng, cluster cần clone phải được setup phù hợp. Vì `pg_basebackup` “yêu cầu” PostgreSQL cung cấp WAL, target cluster phải có ít nhất hai WAL Sender process đang active (WAL Sender process chịu trách nhiệm phục vụ WAL qua một client connection).

Vì vậy, bước đầu tiên cần làm trên database mà bạn muốn backup là kiểm tra configuration parameter `max_wal_senders` (trong file `postgresql.conf`) có giá trị từ 2 trở lên:

[source,text]
....
max_wal_senders = 2
....

Một setting quan trọng khác là cho phép `pg_basebackup` tạo connection tới cluster: tool này không tạo connection với tư cách client thông thường mà với tư cách một “replication” client. Vì vậy, file `pg_hba.conf` phải có một rule cho phép administrative user connect tới database đặc biệt “replication”. Cấu hình tương tự sau đây sẽ hoạt động cho local backup:

[source,text]
....
host      replication         postgres     127.0.0.1/32       trust
....

Ở đây, user `postgres` được phép connect từ chính host đó tới database replication đặc biệt mà không cần cung cấp credential xác thực.

[WARNING]
====
Một replication connection có thể sao chép toàn bộ data từ database, vì vậy phải được bảo vệ ở mức cao nhất có thể. Trong production environment, luôn giới hạn các host được phép tạo replication connection, đồng thời thiết lập credential mạnh để xác thực connection!

====
Giả sử chúng ta muốn thực hiện physical backup và lưu kết quả, tức bản thân backup, trong directory `/backup/data`. Để thực hiện backup, target directory phải tồn tại; nếu database có tablespace, từng directory của tablespace phải được remap sang một directory khác. Điều này bắt buộc vì chúng ta đang backup trên cùng host, nên PostgreSQL ngăn các directory bị trùng với nhau.

Backup cũng cần một label, tức một mô tả gợi nhớ về mục đích của backup, chỉ để con người dễ đọc.

[quote]
____
Trong Docker image của chương này, các directory cần thiết cho backup và tablespace remapping đã được cấu hình sẵn.

____

Flag `-D` chỉ định directory nơi bạn muốn lưu backup, trong ví dụ này là `/backup/data`. Flag tùy chọn `-l` cho phép cung cấp một label dạng text cho backup; label này có thể dùng để kiểm tra backup và lấy thêm thông tin. Flag `-v` bật verbose mode, tạo output chi tiết về những gì command thực hiện ở từng bước. Flag `-T` được lặp lại để cho PostgreSQL biết cách remap từng directory được dùng làm tablespace: directory ở bên trái dấu bằng là directory hiện tại nơi backup được lấy, còn directory ở bên phải là remapped path.

Các argument còn lại là những client flag điển hình của PostgreSQL libpq, dùng để chỉ định cách tạo connection tới database cần clone; trong trường hợp này, connection được thực hiện thông qua user `postgres` trên `localhost`, port `5432`.

[quote]
____
`pg_basebackup` hỗ trợ một số option khác, chẳng hạn để giới hạn mức sử dụng network bandwidth hoặc hiển thị tiến trình của các backup đang diễn ra, cùng nhiều tính năng khác. Hãy tham khảo command documentation và online help để biết thêm chi tiết.

____
Nếu kiểm tra directory nơi backup được lưu, bạn sẽ thấy đó thực sự là một clone của directory `PGDATA` của server mà bạn đã backup, bao gồm cả configuration file.

== `pg_verifybackup`

Từ PostgreSQL 13, bạn có thể dùng tool có tên `pg_verifybackup` để kiểm tra integrity của backup được thực hiện bằng `pg_basebackup`. Nhìn chung, tool này hoạt động như sau:

[source,console,role="transcript"]
....
$ pg_verifybackup /backup/data/
backup successfully verified
....

.Command
[source,bash]
....
pg_verifybackup /backup/data/
....

.Output
[source,output]
....
backup successfully verified
....


Khi chỉ định directory chứa backup, tool có thể kiểm tra và báo cáo mọi corruption. Tool thực hiện bốn bước chính:

. Đọc backup manifest để kiểm tra file có thể đọc được và chứa thông tin backup hợp lệ hay không.
. Quét nội dung backup để tìm data file bị thiếu hoặc bị sửa đổi (một số configuration file được bỏ qua ở bước này vì user có thể đã thay đổi chúng).
. So sánh checksum của mọi data file với các giá trị trong manifest để bảo đảm các file không bị corrupt.
. Dùng một utility khác là `pg_waldump` để xác minh rằng các WAL record cần thiết để restore backup đều có sẵn và có thể đọc được.

Nhờ `pg_verifybackup`, bạn có thể chắc chắn rằng backup không bị hỏng do sự cố filesystem, disk failure hoặc nguyên nhân nào khác, từ đó có thể tiếp tục sử dụng backup đó.

== Khởi động cluster đã clone

`pg_basebackup` thực hiện clone hoàn chỉnh của target cluster, bao gồm các configuration file. Điều này có nghĩa là configuration của cluster chưa được điều chỉnh cho vị trí của clone, bao gồm data directory và listening option (ví dụ TCP/IP port). Vì vậy, bạn phải cẩn thận khi khởi động cloned cluster vì nó có thể xung đột với cluster gốc, đặc biệt nếu backup được thực hiện local (trên cùng machine).

Trong trường hợp này, bạn có thể chỉnh sửa configuration trước khi thử khởi động backup cluster, thay đổi các setting chính trên command line hoặc chuyển backup sang một remote host.

Nếu muốn khởi động cloned cluster, với giả định cluster vẫn được giữ local như trong phần trước, bạn có thể khởi động lại cluster, chẳng hạn bằng các setting trên command line sau:

[source,console,role="transcript"]
....
$ pg_ctl -D /backup/data/ -o '-p 5433' start
waiting for server to start....
LOG: database system was interrupted; last known up at 2023-07-19
16:43:39 UTC
LOG:      redo starts at 0/2000028
LOG:      consistent recovery state reached at 0/2000138
....

.Command
[source,bash]
....
pg_ctl -D /backup/data/ -o '-p 5433' start
....

.Output
[source,output]
....
waiting for server to start....

Ở đây, server đã được khởi động với directory `PGDATA` đã được clone và TCP/IP port 5433. Nếu kiểm tra log của database cluster, bạn sẽ thấy PostgreSQL cho biết nó đã bị gián đoạn, một redo process đã bắt đầu và hoàn tất. Khi redo hoàn tất, database sẵn sàng hoạt động bình thường. Nói ngắn gọn, đây là tình huống giống crash: physical dump đã sao chép một trạng thái “dirty” của database, nhưng nhờ WAL, nó có thể tự phục hồi.

Bạn sẽ thấy database đã được restore sau một “forced crash”; nghĩa là cloned cluster đã tự phục hồi trong lần khởi động đầu tiên.

== Khôi phục từ physical backup

Nếu cần restore từ một physical backup, bạn phải ghi đè directory `PGDATA` ban đầu bằng bản clone do `pg_basebackup` tạo ra. Đây là một thao tác rất rủi ro vì bạn sẽ mất toàn bộ nội dung của directory `PGDATA` và thay thế nó bằng bản backup, nên nguy cơ xảy ra lỗi rất cao.

Vì lý do đó, thay vì restore online, chúng tôi đề xuất bạn khởi động một cloned cluster ở nơi khác, như đã trình bày trong phần trước, để extract data cần recover rồi chỉ restore phần data đó trên target cluster. Chẳng hạn, bạn có thể khởi động cloned server, dùng `pg_dump` để extract data cần recover, rồi restore phần data đó trên target cluster.

Dĩ nhiên, có những tình huống bạn cần recover toàn bộ cluster và do đó phải ghi đè `PGDATA`, nhưng ngay cả khi đó, chúng tôi vẫn đề xuất sử dụng những tool nâng cao hơn như `pgBackRest`; tool này sẽ điều phối và hỗ trợ cả backup lẫn restore.

Physical backup và restore là những cơ chế rất mạnh, nhưng đòi hỏi bạn phải hiểu sâu những gì diễn ra bên dưới. Vì vậy, hãy dành thời gian thử nghiệm chúng một cách cẩn thận để sẵn sàng áp dụng trong production.
