= Quản lý streaming replication

Trong phần này, chúng ta sẽ tìm hiểu vì sao cần có replica.

image::chapter-17-figure-17-1-000.jpg[Hình 17.1: Sơ đồ primary/replica]

*Hình 17.1: Sơ đồ primary/replica*

Trong môi trường production, bạn thường cần khôi phục hệ thống nhanh nhất có thể sau một system crash. Để làm vậy, cần dùng streaming replication. Hệ thống cần ít nhất hai server: một primary server và một secondary server. Primary server thực hiện mọi operation do application yêu cầu; replica server chỉ sẵn sàng cho read operation và chứa data được sao chép theo thời gian thực.

== Các khái niệm cơ bản về streaming replication

Ý tưởng của streaming replication là sao chép các WAL file từ primary server sang một server khác (replica server).

Replica server ở trạng thái continuous recovery và liên tục replay WAL do primary server truyền tới. Theo cách này, data của primary server được replicate ở dạng binary trên replica server thông qua WAL.

Như đã thấy trong Chapter 15, Backup and Restore, trong một tình huống PITR điển hình, primary lưu các WAL segment ở một nơi, sau đó recovery server lấy chúng bằng các script thủ công:

image::chapter-17-figure-17-2-000.jpg[Hình 17.2: Sơ đồ PITR]

*Hình 17.2: Sơ đồ PITR*

Trong streaming replication, một communication channel được mở giữa replica và primary, qua đó primary gửi các WAL segment:

image::chapter-17-figure-17-3-000.jpg[Hình 17.3: Sơ đồ WAL primary/replica]

*Hình 17.3: Sơ đồ WAL primary/replica*

Replica server nhận các WAL segment và replay chúng, qua đó duy trì permanent recovery state.

Tiếp theo, chúng ta sẽ xem cách thực hiện asynchronous physical replication. Kỹ thuật này rất giống PITR.

== Chuẩn bị môi trường cho asynchronous replication

Hãy chuẩn bị môi trường. Chúng ta cần hai server: server thứ nhất tên pg1, có IP 192.168.122.10; server thứ hai tên pg2, có IP 192.168.122.11. Sau đây là các bước chuẩn bị cho physical replication.

Trên primary server, cần thực hiện các bước sau:

. Trước hết, cần chỉnh `listen_addresses` để PostgreSQL lắng nghe trên network. Nếu đặt `listen_addresses = '*'`, PostgreSQL sẽ lắng nghe trên mọi IP; nếu không, có thể chỉ định một danh sách IP address, phân tách bằng dấu phẩy. Thay đổi này yêu cầu restart PostgreSQL service.

== Tùy chọn wal_keep_segments

Như đã biết, physical replication được thực hiện bằng cách truyền WAL segment. Giả sử replica server bị dừng vì một lý do nào đó. Primary sẽ xử lý ra sao? Khi replica server hoạt động trở lại, nó có tự đồng bộ lại với primary server không? Đây là những câu hỏi cần đặt ra để replication system hoạt động chính xác.

Parameter trong `postgresql.conf` có tên là `wal_keep_segments` và cho PostgreSQL biết cần giữ bao nhiêu WAL segment trên disk; theo mặc định, `wal_keep_segments` bằng zero vì replica không được tạo trong quá trình cài đặt PostgreSQL. Điều này nghĩa là PostgreSQL không lưu thêm WAL segment nào làm buffer. Nếu replica server (standby) bị dừng, nó sẽ không thể đồng bộ lại khi khởi động lại. Lý do là trong thời gian replica cần để hoạt động trở lại, primary server có thể đã tạo và xóa các WAL segment mới. Cách đầu tiên để khắc phục là đặt `wal_keep_segments` thành giá trị lớn hơn zero trong `postgresql.conf`. Ví dụ, nếu đặt `wal_keep_segments = 100`, sẽ có ít nhất 100 file WAL segment trong thư mục `pg_wal`, chiếm tổng cộng 100 * 16 MB = 1.6 GB dung lượng disk.

Trong trường hợp này, primary luôn giữ các WAL segment bổ sung. Nếu replica bị dừng, sau khi hoạt động trở lại, nó chỉ có thể đồng bộ lại nếu primary đã tạo ít hơn `wal_keep_segments` WAL segment.

Giải pháp này cung cấp một static buffer để lưu các WAL segment cũ, tạo ra một khoảng đệm an toàn cho đến khi primary tạo ra số WAL segment vượt quá `wal_keep_segments`. Đây là một static solution; nhược điểm là dung lượng disk luôn bị chiếm dụng ở mức `wal_keep_segments * 16 MB`, ngay cả khi primary server không còn cần giữ các WAL segment nữa (vì replica server đã xử lý chúng). Ưu điểm của giải pháp này là khi network gặp sự cố, PostgreSQL chỉ sử dụng tối đa `wal_keep_segments * 16 MB` dung lượng disk, nhờ đó tránh làm đầy toàn bộ disk nếu primary server bị dừng. Vì vậy, nếu dung lượng disk hạn chế, có thể sử dụng giải pháp này; nhưng cần nhớ rằng nếu lượng WAL vượt quá mức `wal_keep_segments * 16 MB`, replica sẽ không còn được đồng bộ và chúng ta sẽ phải rebuild nó.

== Sử dụng replication slot

Trong PostgreSQL, có một approach khác để giải quyết việc lưu WAL segment: replication slot. Với slot, có thể yêu cầu PostgreSQL giữ mọi WAL segment trên primary cho đến khi chúng được truyền tới replica server. Nhờ đó, cơ chế quản lý số WAL segment mà primary server phải giữ làm buffer trở nên dynamic, linh hoạt và hoàn toàn tự động. Đây là cách đơn giản để quản lý physical replica và là phương pháp mà cuốn sách này sẽ tập trung vào.

Để tạo slot mới, thực hiện statement sau trên PostgreSQL:

[source,console,role="transcript"]
....
postgres=# SELECT * FROM pg_create_physical_replication_slot('master');

-----------+-----
 master    |
(1 row)
....

.SQL
[source,sql]
....
SELECT *
FROM pg_create_physical_replication_slot('master');
....

.Output
[source,output]
....

-----------+-----
 master    |
(1 row)
....


Để drop một slot, thực hiện statement sau:

[source,console,role="transcript"]
....
postgres=# select pg_drop_replication_slot('master');

--------------------------

(1 row)
....

.SQL
[source,sql]

== Sử dụng command pg_basebackup

Trong Chapter 15, Backup and Restore, ở section Basic concepts behind Point In Time Recovery, chúng ta đã nói về base backup. Đây là một hot backup đóng vai trò là base ban đầu để áp dụng tất cả WAL segment. Có một command tên là `pg_basebackup` gần như tự động hóa quy trình này.

Giá trị `max_wal_senders` phải ít nhất bằng 2. Đây là một command rất hữu ích cho DBA vì cho phép thực hiện mọi việc cần thiết chỉ với một command. Chúng ta sẽ sử dụng và giải thích command này kỹ hơn ở section tiếp theo, nơi sẽ triển khai asynchronous physical replication đầu tiên.

Để biết thêm thông tin về command `pg_basebackup`, hãy tham khảo https://www.PostgreSQL.org/docs/current/app-pgbasebackup.html.

== Asynchronous replication

Đến đây, chúng ta đã có mọi thành phần nền tảng cần thiết để nhanh chóng tạo asynchronous physical replication đầu tiên. Theo mặc định, physical replication trong PostgreSQL là asynchronous. Bây giờ hãy bắt đầu triển khai kỹ thuật replication. Sau khi làm theo các bước ở những section trước của chương này, chúng ta có một primary server sẵn sàng cho replica server kết nối tới và một replica sẵn sàng nhận thông tin từ primary. Lúc này, PostgreSQL service trên replica server đã được tắt, còn PGDATA directory đã được tạo, để trống và có permission phù hợp:

. Chuyển tới PGDATA directory với tư cách system user postgres:

[source,console,role="transcript"]

   root@pg2:# su - postgres
   postgres@pg2:~$ cd /var/lib/PostgreSQL/16/main
....

  mode=disable sslsni=1 ssl_min_protocol_version=TLSv1.2 gssencmode=disable
  krbsrvname=postgres target_session_attrs=any load_balance_hosts=disable’

== Synchronous replication

Cho đến đây, chúng ta đã nói về asynchronous replication: primary server truyền thông tin tới standby replica nhưng không biết chắc standby server đã replicate data hay chưa. Trong asynchronous replication, primary server không chờ replica server thực sự replicate data. Trong synchronous replication, khi primary thực hiện một commit, mọi replica server cũng commit theo cách synchronous. Sau khi commit hoàn tất, ta chắc chắn rằng data đã được replicated trên primary và tất cả replica. Để đạt được synchronous replication, nên có các server giống hệt nhau và một network connection tốt giữa chúng; nếu không, performance có thể giảm.

== Cấu hình PostgreSQL

Dựa trên configuration đã thiết lập cho asynchronous replication, chỉ cần thay đổi một vài setting là có thể chuyển từ asynchronous replication sang synchronous replication.

== Primary server

Trên primary server, cần kiểm tra parameter `synchronous_commit` có được set thành `on` hay không. Hiện tại, `synchronous_commit = on` là giá trị default trong một PostgreSQL installation mới.

Sau khi set parameter này, cần thêm parameter `synchronous_standby_names`, liệt kê tên của tất cả standby server sẽ replicate data theo cách synchronous. Cũng có thể dùng wildcard `*`, qua đó cho PostgreSQL biết rằng mọi standby server đều có thể là một synchronous replica. Ví dụ, để chuyển primary trong ví dụ trước sang dạng có thể hỗ trợ asynchronous replication cho server `pg2`, cần viết như sau:

[source,text]
....
synchronous_standby_names = 'pg2'
synchronous_commit = on
....

Sau đó, cần restart server:

[source,console,role="transcript"]
....
# systemctl restart postgresql
....

.Command
[source,bash]
....
systemctl restart postgresql
....


== Standby server

Trên standby server, cần thêm một parameter vào connection string tới primary để primary biết request đến từ đâu. Cần edit file `postgresql.auto.conf`; hiện tại file này như sau:

[source,console,role="transcript"]

== Cascading replication

Chúng ta đã tìm hiểu cách tạo asynchronous replica từ một primary server. Tuy nhiên, trong một số trường hợp, có thể cần nhiều asynchronous replica. Cách đơn giản nhất là kết nối replica server thứ hai với primary server bằng quy trình vừa trình bày. Tuy nhiên, quy trình này có thể làm tăng load trên primary server, vì vậy PostgreSQL cung cấp một giải pháp thay thế: cascading physical replication. Schema cần đạt được như sau:

image::chapter-17-figure-17-4-000.jpg[Hình 17.4: Cascading replication]

*Hình 17.4: Cascading replication*

Để ví dụ này hoạt động, chúng ta sẽ dùng server thứ ba có tên `pg3`.

Các server có IP như sau:

* `PRIMARY (pg1): IP 192.168.122.10`
* `First replica (pg2): IP 192.168.122.11`
* `Second replica (pg3): IP 192.168.122.12`

== Delayed replication

Trong một số trường hợp, delayed replica có thể hữu ích. Trong PostgreSQL, có thể dùng `recovery_min_apply_delay` trong setting của replica server để đạt mục tiêu này.

Ví dụ, trên replica server, nếu đặt setting này ở cuối file `postgresql.conf`:

[source,text]
....
recovery_min_apply_delay = 5000
....

sau đó reload PostgreSQL service trên replica server:

[source,text]
....
root@pg2:~# systemctl reload postgresql
....

ta có thể thấy replica chậm hơn primary 5 giây vì đơn vị thời gian của `recovery_min_apply_delay` là milliseconds.

Dùng delay trên replica server nghĩa là các WAL file vẫn thường xuyên được tải xuống từ primary server, nhưng chỉ được xử lý sau khoảng delay được chỉ định bởi parameter `recovery_min_apply_delay`.

== Promote replica server thành primary

Nếu primary ngừng hoạt động, log của replica server sẽ ghi nhận error sau:

[source,text]
....
LOG:   waiting for WAL to become available at 0/4000078
2023-05-23 07:22:14.813 UTC [1137] FATAL: could not connect to the
primary server: connection to server at "192.168.122.10", port 5432
failed: No route to host
Is the server running on that host and accepting TCP/IP connections?
....

Điều này có nghĩa là replica server không còn nhận WAL file từ primary. Nếu xảy ra tình huống này, có thể promote replica node thành primary. Để làm vậy, trên replica node, với tư cách postgres user, cần thực thi statement sau:

[source,console,role="transcript"]
....
postgres@pg2:~$ pg_ctl promote -D /var/lib/PostgreSQL/16/main
....

.Command
[source,bash]
....

....


[source,text]

server promoted

* PostgreSQL không tự động thực hiện quy trình này (nếu không có third-party tool).
* Sau khi promote standby replica thành primary, primary cũ trở nên unrecoverable.
* Nếu primary ngừng hoạt động, có thể mất data nếu chưa đồng bộ toàn bộ WAL file trước khi server ngừng hoạt động.
