= Tìm hiểu logical backup

PostgreSQL cung cấp đầy đủ các tool cần thiết để thực hiện logical backup và restore. Nhiều operating system, bao gồm FreeBSD và Debian GNU/Linux, cung cấp script và wrapper cho các tool backup và restore của PostgreSQL để system administrator lên lịch backup và restore. Các script và wrapper này không được giải thích ở đây. Để biết thêm thông tin, hãy đọc package documentation về PostgreSQL của operating system bạn đang sử dụng.

Ba ứng dụng chính phục vụ các thao tác backup và restore là `pg_dump`, `pg_dumpall` và `pg_restore`. Như tên gọi gợi ý, `pg_dump` và `pg_dumpall` dùng để trích xuất (dump) nội dung của một database, qua đó tạo ra một backup; `pg_restore` là ứng dụng tương ứng, cho phép bạn restore một backup hiện có.

[quote]
____
*Lưu ý:* Version của tool rất quan trọng; bạn luôn nên dùng các tool cùng major version với PostgreSQL. Bạn có thể dùng tool từ version mới hơn để thực hiện backup cho các cluster cũ hơn, nhưng không thể làm theo chiều ngược lại.

____
Không giống các database engine khác, PostgreSQL không yêu cầu một privilege đặc biệt có tên “backup” để dump nội dung của một database: user thực hiện backup chỉ cần có đủ privilege để truy cập data mà họ muốn backup. Tương tự, để restore data, user phải có đủ privilege để ghi data vào các table. Tuy nhiên, để đơn giản hóa việc quản lý privilege, PostgreSQL cung cấp hai role đặc biệt được định nghĩa sẵn là `pg_read_all_data` và `pg_write_all_data`. Có thể grant các role này cho user cần thực hiện backup và/hoặc restore; các role này sẽ tự động cung cấp cho user mọi quyền cần thiết để đọc hoặc ghi data.

Ứng dụng `pg_dump` dùng để dump một database đơn lẻ trong một cluster, `pg_dumpall` cung cấp cách thuận tiện để dump toàn bộ nội dung cluster, bao gồm các role và các object khác ở cấp cluster, còn `pg_restore` có thể xử lý output của hai ứng dụng này để thực hiện restore.

[quote]
____
*Lưu ý:* Hãy nhớ rằng một backup chỉ hợp lệ khi có thể restore thành công. `pg_dump` và `pg_dumpall` sẽ không tạo ra backup bị corrupt, nhưng storage có thể vô tình làm hỏng các file backup; vì vậy, để bảo đảm backup hợp lệ, bạn luôn nên thử restore backup đó trên một machine hoặc cluster khác.

____
Cả ba command đều có thể hoạt động trên cluster local hoặc remote để backup hoặc restore data. Điều đó có nghĩa là bạn có thể dùng chúng từ một backup machine remote hoặc ngay trên server đang chạy cluster. Các ứng dụng này tuân theo cùng quy ước về parameter và variable như `psql`; chẳng hạn, bạn có thể chỉ định username thực hiện backup (hoặc restore) bằng flag command-line `-U`, cũng như chỉ định remote host nơi cluster đang chạy bằng `-h`, v.v. Nếu không cung cấp parameter nào, ứng dụng giả định cluster đang chạy local và kết nối tới cluster bằng user của operating system hiện tại, giống như `psql`.

Ở các subsection tiếp theo, bạn sẽ học cách backup và restore các database của mình.

== Dump một database đơn lẻ

Để dump, tức tạo một bản backup của một database, bạn cần dùng command `pg_dump`.

`pg_dump` cho phép dùng các backup format chính sau đây; chỉ format đầu tiên phù hợp để restore mà không cần `pg_restore`:

* *Plain text format:* Backup gồm các SQL statement có thể dùng để tái tạo database và được biểu diễn dưới dạng plain text SQL. Backup tạo ra có thể ở dạng plain text hoặc được compressed ngay trong quá trình tạo.
* *Directory format:* Backup được đặt trong một directory cụ thể; mỗi table và large object của database được đặt trong một file compressed.
* *Custom format:* Đây là format đặc thù của PostgreSQL, phù hợp cho selective restore bằng `pg_restore`.
* *Tar format:* Phiên bản `tar(1)` của directory format nói trên.

Theo mặc định, `pg_dump` dùng plain text format. Format này tạo ra các SQL statement có thể dùng để dựng lại structure và content của database, đồng thời xuất backup trực tiếp ra standard output. Nghĩa là nếu bạn backup một database mà không chỉ định option cụ thể nào, bạn sẽ thấy một danh sách dài các SQL statement:

Như bạn thấy, `pg_dump` đã tạo ra một tập hợp các SQL statement theo đúng thứ tự. Nếu đưa chúng vào một connection interactive, các statement này cho phép bạn dựng lại không chỉ database structure (table và function) mà còn cả content (data trong table), privilege (grant và revoke) cùng các object cần thiết khác. Tất cả các dòng bắt đầu bằng hai dấu gạch ngang là SQL comment mà `pg_dump` cẩn thận thêm vào để giúp bạn phân tích và hiểu nội dung của backup database.

Liên quan đến nội dung của backup, có vài điểm quan trọng cần lưu ý. Trước hết, `pg_dump` đặt một loạt `SET` statement ngay đầu backup; các `SET` statement này không bắt buộc để tạo backup nhưng cần thiết khi restore nội dung backup. Nói cách khác, một vài dòng đầu của backup không mô tả nội dung mà mô tả cách sử dụng backup.

Một `SET` statement quan trọng trong số đó là dòng sau, được giới thiệu trong các version gần đây của PostgreSQL:

[source,sql]
....
SELECT pg_catalog.set_config('search_path', '', FALSE);
....

Các dòng như vậy loại bỏ (tức làm rỗng) biến `search_path`, vốn là danh sách tên schema dùng để tìm một object chưa được qualify. Nhờ đó, khi restore, các object được tạo từ backup sẽ không khai thác malicious code có thể đã xâm nhập vào environment và `search_path` của bạn. Tác động phụ của việc này, như sẽ trình bày sau, là sau khi restore, user sẽ có một search_path rỗng và không thể tìm các object chưa được fully qualify bằng tên.

Một điểm quan trọng khác về content của backup là theo mặc định, `pg_dump` dùng `COPY` để insert data vào từng table. `COPY` là một PostgreSQL command hoạt động tương tự `INSERT`, cho phép chỉ định nhiều tuple cùng lúc và, quan trọng nhất, được tối ưu cho bulk loading, nhờ đó recovery nhanh hơn. Tuy nhiên, điều này có thể khiến backup không portable giữa các database engine khác nhau. Vì vậy, nếu mục tiêu là dump content của database để migrate sang engine khác, bạn phải yêu cầu `pg_dump` dùng các `INSERT` statement thông thường thông qua flag command-line `--insert`:

Dump nội dung của database là việc hữu ích, nhưng lưu nội dung đó vào một file còn hữu ích hơn vì cho phép restore về sau. Có hai cách chính để lưu output của `pg_dump` vào một file. Một cách là redirect output vào file, như trong ví dụ sau:

[source,console,role="transcript"]
....
$ pg_dump --column-inserts forumdb > backup_forumdb.sql
....

.Command
[source,bash]

[source,console,role="transcript"]

$ pg_dump --column-inserts -f backup_forumdb.sql forumdb
....

.Command

Sau khi chuẩn bị xong file backup, bạn có thể dễ dàng restore file đó. Chúng ta sẽ học cách thực hiện việc này trong section tiếp theo.

== Restore một database đơn lẻ

Nếu backup bạn tạo là plain SQL, bạn không cần gì ngoài một database connection để restore; chỉ cần thực thi một loạt statement theo đúng thứ tự là có thể tạo lại content của database.

Cần lưu ý rằng theo mặc định, `pg_dump` không phát hành statement `CREATE DATABASE` trong content backup. Giả sử chúng ta tạo một backup file như sau:

[source,console,role="transcript"]
....
$ pg_dump --column-inserts -f backup_forumdb.sql forumdb
....

.Command
[source,bash]
....
pg_dump --column-inserts -f backup_forumdb.sql forumdb
....


File `backup_forumd.sql` được tạo ra sẽ không bao gồm bất kỳ lệnh nào về cách tạo một database mới. Điều này có thể tiện lợi nhưng cũng nguy hiểm: restore sẽ diễn ra bên trong database mà bạn đang kết nối tới.

[quote]
____
*Lưu ý:* `pg_dump` đủ thông minh để xác định đúng thứ tự dump các table và object khác, bảo đảm dependency của chúng có thể được restore đúng thứ tự.

____
Giả sử muốn restore content của database vào một database local khác có tên `forumdb_restore`. Bước đầu tiên là tạo database như sau:

[source,console,role="transcript"]

$ psql -c 'CREATE DATABASE forumdb_restore WITH OWNER forum;'

Như bạn thấy, output của `pg_dump` hiện bao gồm việc tạo database, cũng như command đặc biệt `\c` để kết nối ngay tới database đó. Nói cách khác, khi chạy file này qua `psql`, nó sẽ restore toàn bộ content vào đúng database nếu database đó chưa tồn tại.

Để kiểm thử việc này, hãy xóa database thân yêu của chúng ta rồi restore nó bằng cách trước tiên kết nối tới `template1`:

[source,console,role="transcript"]
....
$ psql -c 'DROP DATABASE forumdb';
DROP DATABASE
$ psql
postgres=# \i backup_forumdb.sql
...
forumdb=#
....

.Command
[source,bash]
....
psql -c 'DROP DATABASE forumdb';
psql
....

.SQL
[source,sql]
....
\i backup_forumdb.sql
....

.Output
[source,output]
....
DROP DATABASE
...
....


Hãy chú ý rằng command prompt đã thay đổi, phản ánh việc hiện tại chúng ta đang kết nối tới database `forumdb` đã được restore.

Vậy nên dùng version nào của tool dump và restore? Nếu replicate database trong một cluster khác, chẳng hạn để migrate một staging database sang production, bạn nên bao gồm option `--create` để database engine tự tạo database cho bạn. Nếu migrate content của database vào một database đã tồn tại, tuyệt đối không được dùng option `--create`, vì không cần thiết lập database; điều này có thể gây rủi ro vì bạn có thể restore object vào nhầm database, nên cần kiểm tra cẩn thận rằng bạn đang kết nối tới đúng database trước khi reload backup script.

Nếu migrate content của database sang engine khác, chẳng hạn một relational database khác, bạn nên dùng các option như `--inserts` hoặc `--column-inserts` để làm cho database backup portable hơn.

== Giới hạn lượng data cần backup

`pg_dump` cho phép dùng một tập hợp phong phú các filter và flag để giới hạn lượng data cần backup. Chẳng hạn, bạn có thể chỉ dump schema của database mà không dump data nào; việc này có thể thực hiện bằng flag `-s`. Ngược lại, có thể schema của database đã tồn tại và bạn chỉ cần content của database mà không cần bất kỳ DDL statement nào; việc này có thể thực hiện bằng option `-a`. Tất nhiên, bạn có thể kết hợp các command `pg_dump` khác nhau để tạo các backup riêng biệt:

[source,console,role="transcript"]
....
$ pg_dump -s -f database_structure.sql forumdb
$ pg_dump -a -f database_content.sql forumdb
....

.Command
[source,bash]
....
pg_dump -s -f database_structure.sql forumdb
pg_dump -a -f database_content.sql forumdb
....


Bạn sẽ có một file tên `database_structure.sql` chứa mọi `CREATE TABLE` statement, và một file khác chỉ chứa các statement `COPY` (hoặc `INSERT` nếu bạn đã chỉ định `--inserts`).
Bạn cũng có thể quyết định giới hạn phạm vi backup, theo schema hoặc data, đối với một số table bằng flag command-line `-t`; hoặc ngược lại, loại trừ một số table bằng parameter `-T`. Ví dụ, nếu chỉ muốn backup table `users` và sequence `users_pk_seq`, bạn có thể làm như sau:

[source,console,role="transcript"]
....
$ pg_dump -f users.sql -t forum.users -t forum.user_pk_seq forumdb
....

.Command
[source,bash]
....
pg_dump -f users.sql -t forum.users -t forum.user_pk_seq forumdb
....


File `users.sql` được tạo sẽ chỉ chứa đủ data để tạo lại các thành phần liên quan đến user, không hơn. Ngược lại, nếu muốn loại trừ table `users` khỏi backup, bạn có thể làm tương tự như sau:

[source,console,role="transcript"]
....
$ pg_dump -f users.sql -T forum.users -T forum.user_pk_seq forumdb
....

.Command
[source,bash]
....
pg_dump -f users.sql -T forum.users -T forum.user_pk_seq forumdb
....


Dĩ nhiên, bạn có thể kết hợp các option theo cách phù hợp với nhu cầu và, quan trọng hơn, restore chính xác những gì cần thiết. Ví dụ, nếu muốn lấy toàn bộ data trong table `posts` cùng với structure của table đó, bạn có thể làm như sau:

[source,console,role="transcript"]
....
$ pg_dump -f posts.sql -t forum.posts -a -v forumdb
...
pg_dump: warning: there are circular foreign-key constraints on this
table:
pg_dump:      posts
pg_dump: You might not be able to restore the dump without using
--disable-triggers or temporarily dropping the constraints.
pg_dump: Consider using a full dump instead of a --data-only dump to avoid
this problem.
....

.Command
[source,bash]
....
pg_dump -f posts.sql -t forum.posts -a -v forumdb
....

.Output
[source,output]
....
...
pg_dump: warning: there are circular foreign-key constraints on this
table:
pg_dump:      posts
pg_dump: You might not be able to restore the dump without using
--disable-triggers or temporarily dropping the constraints.
pg_dump: Consider using a full dump instead of a --data-only dump to avoid
this problem.
....


`pg_dump` đủ thông minh để nhận ra table `posts` có các dependency và foreign key khác nhau, nên cảnh báo rằng dump của bạn có thể không restore được toàn bộ content của table `posts`. Bạn phải tự quản lý các dependency đó đúng cách, vì bạn đã yêu cầu `pg_dump` không thực hiện full backup (vốn luôn đầy đủ và nhất quán).

== Compression

`pg_dump` cung cấp một command-line option đặc biệt là `-Z`, nhận một số nguyên từ 0 đến 9 để chỉ định compression level cho backup được tạo. Level 0 nghĩa là hoàn toàn không compression, còn 9 là mức compression cao nhất hiện có.

Để minh họa compression hoạt động thế nào, giả sử chúng ta tạo hai backup của cùng một database: backup thứ nhất không compression, backup thứ hai có compression (hãy chú ý command-line option và filename thay đổi):

[source,console,role="transcript"]
....
$ pg_dump -f backup_forumdb_uncompressed.sql forumdb
$ pg_dump -f backup_forumdb_compressed.sql.gz -Z 9 forumdb
$ ls -1s backup_forumdb*
4 backup_forumdb_compressed.sql.gz
12 backup_forumdb_uncompressed.sql
....

.Command
[source,bash]
....
pg_dump -f backup_forumdb_uncompressed.sql forumdb
pg_dump -f backup_forumdb_compressed.sql.gz -Z 9 forumdb
ls -1s backup_forumdb*
....

.Output
[source,output]
....
4 backup_forumdb_compressed.sql.gz
12 backup_forumdb_uncompressed.sql
....


Như bạn có thể thấy, file đã được nén chỉ chiếm một phần ba dung lượng của plain backup, nhưng lần này file không thể chỉnh sửa trực tiếp vì được lưu ở dạng binary.

Có thể áp dụng compression cho plain text (tức SQL) dump và directory format, nhưng không áp dụng được cho tar output format.

== Các format dump và pg_restore

Trong các phần trước, bạn chỉ thấy plain SQL format dùng cho backup và restore, nhưng `pg_dump` còn cung cấp các format phức tạp và thông minh hơn. Mọi format ngoại trừ plain SQL đều phải dùng `pg_restore` để restore, nên không phù hợp cho việc chỉnh sửa thủ công.

Backup format được chỉ định bằng command-line argument `-F` của `pg_dump`, cho phép dùng một trong các giá trị sau:

* `c` (custom) là format đặc thù của PostgreSQL trong một single-file archive.
* `d` (directory) là format đặc thù của PostgreSQL có compression, trong đó mỗi object được tách thành một file riêng bên trong một directory.
* `t` (tar) là format `.tar` không compression; sau khi extract, nó tạo ra layout giống layout do directory format cung cấp.

Hãy bắt đầu với format đầu tiên: custom single-file format. Command để backup một database tương tự command dùng cho plain SQL format, trong đó phải chỉ định output file, nhưng lần này file không phải plain text:

[source,console,role="transcript"]
....
$ pg_dump -Fc --create -f backup_forumdb.backup forumdb
....

.Command
[source,bash]
....
pg_dump -Fc --create -f backup_forumdb.backup forumdb
....


Output file được tạo có kích thước nhỏ hơn plain SQL file và không thể chỉnh sửa dưới dạng text vì là binary. Nhiều command-line argument của `pg_dump` áp dụng tương tự cho custom format, trong khi một số argument khác hoàn toàn không có ý nghĩa.

Trong mọi trường hợp, `pg_dump` đủ thông minh để biết cần xem xét và loại bỏ điều gì, vì vậy các command line sau sẽ tạo ra cùng backup như trong ví dụ trước:

[source,console,role="transcript"]
....
$ pg_dump -Fc --create --inserts -f backup_forumdb.backup forumdb
$ pg_dump -Fc --create --column-inserts -f backup_forumdb.backup forumdb
....

.Command
[source,bash]
....
pg_dump -Fc --create --inserts -f backup_forumdb.backup forumdb
pg_dump -Fc --create --column-inserts -f backup_forumdb.backup forumdb
....


Rõ ràng, các flag command-line `--column-inserts` và `--inserts` không có ý nghĩa với loại backup này, vì không có text file (và do đó không có SQL statement) nào được tạo.

Khi đã có custom backup, làm thế nào để restore content của database? Hãy nhớ rằng custom backup format yêu cầu dùng `pg_restore` để restore thành công. Như trước, hãy xóa database rồi restore lại bằng `pg_restore`:

[source,console,role="transcript"]
....
$ psql -c 'DROP DATABASE forumdb';
DROP DATABASE
$ pg_restore -C -d postgres backup_forumdb.backup
....

.Command
[source,bash]
....
psql -c 'DROP DATABASE forumdb';
pg_restore -C -d postgres backup_forumdb.backup
....

.Output
[source,output]
....
DROP DATABASE
....


`pg_restore` chạy im lặng và restore database được chỉ định. Option `-C` cho biết `pg_restore` sẽ tạo lại database trước khi restore object vào đó. Option `-d` yêu cầu program trước tiên kết nối tới database `postgres`, phát hành một `CREATE DATABASE`, sau đó kết nối tới database mới được tạo để tiếp tục restore, tương tự cách plain backup format đã làm. Rõ ràng, `pg_restore` yêu cầu file backup làm argument bắt buộc, tức argument cuối cùng được chỉ định trên command line.

Điều thú vị là `pg_restore` có thể tạo một danh sách SQL statement thay vì thực thi trực tiếp chúng. Command-line option `-f` thực hiện việc này, cho phép bạn lưu plain SQL vào một file hoặc kiểm tra plain SQL đó trước khi tiếp tục quá trình restore:

[source,console,role="transcript"]
....
$ pg_restore backup_forumdb.backup -f restore.sql
$ less restore.sql
--
-- PostgreSQL database dump
--

CREATE DATABASE forumdb WITH TEMPLATE = template0 ENCODING = 'UTF8'
LOCALE_PROVIDER = libc LOCALE = 'en_US.utf8';


ALTER DATABASE forumdb OWNER TO forum;


\connect forumdb


...
....

.Command
[source,bash]
....
pg_restore backup_forumdb.backup -f restore.sql
less restore.sql
....

.Output
[source,output]
....
--
-- PostgreSQL database dump
--

CREATE DATABASE forumdb WITH TEMPLATE = template0 ENCODING = 'UTF8'
LOCALE_PROVIDER = libc LOCALE = 'en_US.utf8';


ALTER DATABASE forumdb OWNER TO forum;


\connect forumdb


...
....


Như bạn có thể thấy, content của file `restore.sql` là plain SQL, tương tự output của plain dump do `pg_dump` tạo ra. Điều đó có nghĩa là khi dùng `pg_restore`, bạn luôn có thể lấy ra một danh sách SQL statement có thể chỉnh sửa và dễ đọc từ một backup.

Một output format khác của `pg_dump` là directory format, được chỉ định bằng command-line flag `-Fd`. Ở format này, `pg_dump` tạo một tập các file compressed trong một directory trên disk; trong trường hợp này, command-line argument `-f` chỉ định tên của một directory thay vì một file duy nhất. Ví dụ, hãy backup vào một directory backup:

[source,console,role="transcript"]
....
$ pg_dump -Fd -f backup.d forumdb
$ ls -1s backup.d/

4 3368.dat.gz
4 3370.dat.gz
4 3371.dat.gz
4 3372.dat.gz
4 3373.dat.gz
4 3375.dat.gz
4 3377.dat.gz
12 toc.dat
....

.Command
[source,bash]
....
pg_dump -Fd -f backup.d forumdb

....

.Output
[source,output]
....

4 3368.dat.gz
4 3370.dat.gz
4 3371.dat.gz
4 3372.dat.gz
4 3373.dat.gz
4 3375.dat.gz
4 3377.dat.gz
12 toc.dat
....


Directory được tạo nếu cần, và mỗi database object được đặt trong một compressed file riêng. File `toc.dat` đại diện cho một ToC, một index cho `pg_restore` biết nơi tìm từng phần data bên trong directory. Ví dụ sau cho thấy cách xóa và restore database bằng backup ở directory format:

[source,console,role="transcript"]
....
$ psql -c "DROP DATABASE forumdb;"
DROP DATABASE
$ pg_restore -C -d postgres backup.d
....

.Command
[source,bash]
....
psql -c "DROP DATABASE forumdb;"
pg_restore -C -d postgres backup.d
....

[source,output]
....

....


Directory format hữu ích khi database tăng kích thước, vì việc lưu một file khổng lồ duy nhất có thể trở thành vấn đề do vượt quá giới hạn của filesystem.

Format cuối cùng của `pg_dump` là `.tar`, có thể lấy bằng command-line flag `-Ft`. Kết quả là một uncompressed `tar(1)` archive chứa cùng directory structure như trong ví dụ trước, nhưng mọi file đều không compressed:

[source,console,role="transcript"]
....
$ pg_dump -Ft -f backup_forumdb.tar forumdb
$ tar -tf backup_forumdb.tar
toc.dat
3368.dat
3370.dat
3371.dat
3372.dat
3373.dat
3375.dat
3377.dat
....

.Command
[source,bash]
....
pg_dump -Ft -f backup_forumdb.tar forumdb
tar -tf backup_forumdb.tar

[source,output]
....

3372.dat
3373.dat
3375.dat
3377.dat
