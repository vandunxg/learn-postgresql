= Các isolation level của transaction

Trong một database system có các transaction chạy đồng thời, bạn có thể gặp ba vấn đề khác nhau:

* *Dirty reads:* Dirty read xảy ra khi database cho phép một transaction nhìn thấy data đang được các transaction khác xử lý nhưng chưa hoàn tất. Nói cách khác, data chưa được consolidate đã hiển thị cho các transaction khác. Không database nào sẵn sàng đưa vào production cho phép điều đó, và PostgreSQL cũng không ngoại lệ: bạn có thể yên tâm rằng transaction của mình chỉ nhìn thấy data đã được consolidate; để data được consolidate, các transaction đã tạo ra data đó phải hoàn tất.
* *Unrepeatable reads:* Unrepeatable read xảy ra khi cùng một query, trong cùng một transaction, được thực thi nhiều lần nhưng nhìn thấy các tập data khác nhau. Về bản chất, điều này có nghĩa là data đã thay đổi giữa hai lần thực thi liên tiếp của cùng một query trong cùng transaction. PostgreSQL ngăn vấn đề này nhờ snapshot: mỗi transaction có thể nhìn thấy snapshot của data hiện có, tùy thuộc vào boundary cụ thể của transaction.
* *Phantom reads:* Phantom read tương tự unrepeatable read, nhưng thứ thay đổi giữa các lần thực thi liên tiếp của cùng một query là kích thước của result set. Điều đó có nghĩa là data không thay đổi, nhưng data mới đã được thêm vào result set của lần thực thi trước.

SQL standard cung cấp bốn isolation level mà một transaction có thể chọn để ngăn các vấn đề nêu trên:

* *Read uncommitted:* Level thấp nhất có thể.
* *Read committed:* Isolation level mặc định trong PostgreSQL.
* *Repeatable read:* Hữu ích cho các job chạy trong thời gian dài, vì system không nhìn thấy ảnh hưởng của các transaction đồng thời; nhờ đó, chúng ta có thể làm việc trên một snapshot nhất quán trong suốt thời gian transaction thực thi.
* *Serializable:* Isolation level mạnh nhất hiện có.

Mỗi level cung cấp mức isolation cao hơn level trước đó; ví dụ, `READ COMMITTED` bao gồm hành vi của `READ UNCOMMITTED`, `REPEATABLE READ` bao gồm `READ COMMITTED` (và `READ UNCOMMITTED`), còn `SERIALIZABLE` bao gồm tất cả các level trước đó.

PostgreSQL không hỗ trợ tất cả các level nêu trên, như sẽ được trình bày chi tiết trong các subsection sau. Bạn luôn có thể chỉ định isolation level mong muốn cho một explicit transaction ngay khi transaction bắt đầu; mọi isolation level đều có đúng tên như trong danh sách trên. Ví dụ, lệnh sau bắt đầu một transaction ở mode `READ` committed:

[source,console,role="transcript"]
....
forumdb=> BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN
....

.SQL
[source,sql]
....
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
....

.Output
[source,output]
....
BEGIN
....


Bạn có thể bỏ keyword tùy chọn `TRANSACTION`, dù theo chúng tôi giữ keyword này giúp câu lệnh dễ đọc hơn. Cũng có thể chỉ định rõ isolation level của transaction bằng statement `SET TRANSACTION`. Ví dụ, snippet sau có tác dụng giống ví dụ trước:

[source,console,role="transcript"]
....
forumdb=> BEGIN;
BEGIN
forumdb=> SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET
....

.SQL
[source,sql]
....
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
....

.Output
[source,output]
....
BEGIN
SET
....


Cần lưu ý rằng không thể thay đổi isolation level của transaction sau khi transaction đã bắt đầu. Để có tác dụng, statement `SET TRANSACTION` phải là statement đầu tiên được thực thi trong một transaction block. Mọi statement `SET TRANSACTION` tiếp theo nếu thay đổi isolation level đã được thiết lập sẽ thất bại và đưa transaction vào trạng thái abort; nếu statement `SET TRANSACTION` tiếp theo không thay đổi isolation level, nó sẽ không có tác dụng và cũng không tạo lỗi.

Để hiểu rõ hơn trường hợp này, dưới đây là một workflow không hợp lệ: isolation level bị thay đổi sau khi transaction đã thực thi một statement, dù statement đó không thay đổi data:

[source,console,role="transcript"]
....
forumdb=> BEGIN;
BEGIN
forumdb=> SELECT count(*) FROM tags;
   count
-------
     7
(1 row)
-- a query has been executed, the SET TRANSACTION
-- is not anymore the very first command
forumdb=> SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
ERROR:        SET TRANSACTION ISOLATION LEVEL must be called before any query
....

.SQL
[source,sql]
....
BEGIN;
SELECT count(*)
FROM tags;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
....

.Output
[source,output]
....
BEGIN
   count
-------
     7
(1 row)
-- a query has been executed, the SET TRANSACTION
-- is not anymore the very first command
ERROR:        SET TRANSACTION ISOLATION LEVEL must be called before any query
....


Trong các phần sau, chúng ta sẽ thảo luận chi tiết về từng isolation level.

== READ UNCOMMITTED

Isolation level `READ UNCOMITTED` khiến transaction có thể gặp vấn đề dirty read, nghĩa là transaction đó có thể nhìn thấy data chưa được consolidate từ các transaction khác chưa hoàn tất.

PostgreSQL không hỗ trợ isolation level này vì suy cho cùng, đây không phải là một isolation level thực sự. Thực tế, `READ UNCOMMITTED` có nghĩa là hoàn toàn không có isolation giữa các transaction, và đây chắc chắn là tình huống dẫn đến data corruption do các thay đổi bị interleave.

Bạn có thể set isolation level một cách rõ ràng, nhưng PostgreSQL sẽ bỏ qua yêu cầu đó và âm thầm chuyển level thành `READ COMMITTED` mạnh hơn.

== READ COMMITTED

Isolation level `READ COMMITTED` là isolation level mặc định mà PostgreSQL sử dụng; nếu bạn không set level, mọi transaction (implicit hoặc explicit) đều sẽ dùng isolation level này.

Level này ngăn dirty reads và cho phép transaction hiện tại nhìn thấy toàn bộ data đã được consolidate mỗi khi một statement đơn lẻ trong transaction được thực thi. Chúng ta đã thấy điều này trong thực tế ở ví dụ về session đồng thời.

== REPEATABLE READ

Isolation level `REPEATABLE READ` quy định rằng mọi statement trong một transaction chỉ nhìn thấy data đã được consolidate tại thời điểm transaction bắt đầu hoặc, chính xác hơn, tại thời điểm statement đầu tiên của transaction bắt đầu.

== SERIALIZABLE

Isolation level `SERIALIZABLE` áp dụng level `REPEATABLE READ` và bảo đảm rằng hai transaction chạy đồng thời chỉ có thể hoàn tất thành công khi kết quả cuối cùng sẽ giống với trường hợp hai transaction chạy theo thứ tự tuần tự.

Nói cách khác, nếu hai (hoặc nhiều) transaction có isolation level `SERIALIZABLE` cố sửa cùng một subset data theo cách xung đột, PostgreSQL sẽ bảo đảm chỉ một transaction có thể hoàn tất và khiến transaction còn lại thất bại.

Hãy xem điều này trong thực tế bằng cách tạo transaction đầu tiên rồi sửa một subset data:

[source,console,role="transcript"]
....
-- session 1
forumdb=> BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN
forumdb=> UPDATE tags SET tag = lower( tag );
UPDATE 7
....

.SQL
[source,sql]
....
-- session 1
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
UPDATE tags
SET
    tag = lower(tag);
....

.Output
[source,output]
....
BEGIN
UPDATE 7
....


Để mô phỏng concurrency, hãy tạm dừng transaction này rồi mở một transaction mới trong session khác và áp dụng các thay đổi khác lên cùng tập data:

[source,console,role="transcript"]
....
-- session 2
forumdb=> BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN
forumdb=> UPDATE tags SET tag = '[' || tag || ']';
-- blocked
....

.SQL
[source,sql]
....
-- session 2
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
UPDATE tags
SET
    tag = '[' || tag || ']';
....

.Output
[source,output]
....
BEGIN
-- blocked
....


Vì cùng một tập data được thao tác, transaction thứ hai bị lock, như chúng ta đã thấy trong một ví dụ trước. Bây giờ, giả sử transaction đầu tiên hoàn tất thành công:

[source,console,role="transcript"]
....
-- session 1
forumdb=> COMMIT;
COMMIT
....

.SQL
[source,sql]
....
-- session 1
COMMIT;
....

.Output
[source,output]
....
COMMIT
....


PostgreSQL nhận ra rằng nếu cũng cho transaction kia tiếp tục, điều đó sẽ phá vỡ bảo đảm của `SERIALIZABLE`, vì việc áp dụng các transaction theo thứ tự tuần tự sẽ tạo ra kết quả khác nhau tùy theo thứ tự của chúng.

Vì vậy, ngay khi transaction đầu tiên commit, transaction thứ hai tự động bị abort với một serializable error:

[source,console,role="transcript"]
....
-- session 2
forumdb=> UPDATE tags SET tag = '[' || tag || ']';
ERROR:     could not serialize access due to concurrent update
....

.SQL
[source,sql]
....
-- session 2
UPDATE tags SET tag = '[' || tag || ']';
....

.Output
[source,output]
....
ERROR:     could not serialize access due to concurrent update
....


Điều gì xảy ra nếu transaction thao tác trên data dường như không liên quan? Một transaction vẫn có thể thất bại; thực tế, hãy sửa một tuple duy nhất trong một transaction:

[source,console,role="transcript"]
....
-- session 1
forumdb=> BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN
forumdb=> UPDATE tags SET tag = '{' || tag || '}' WHERE tag = 'java';
UPDATE 1
....

.SQL
[source,sql]
....
-- session 1
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
UPDATE tags
SET
    tag = '{' || tag || '}'
WHERE tag = 'java';
....

.Output
[source,output]
....
BEGIN
UPDATE 1
....


Trong lúc đó, từ một session khác, hãy sửa đúng một tuple khác:

[source,console,role="transcript"]
....
-- session 2
forumdb=> BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN
forumdb=> UPDATE tags SET tag = '[' || tag || ']' WHERE tag = 'perl';
UPDATE 1
....

.SQL
[source,sql]
....
-- session 2
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
UPDATE tags
SET
    tag = '[' || tag || ']'
WHERE tag = 'perl';
....

.Output
[source,output]
....
BEGIN
UPDATE 1
....


Lần này, transaction thứ hai không bị lock vì các tuple bị chạm tới hoàn toàn khác nhau. Tuy nhiên, ngay khi transaction đầu tiên thực thi `COMMIT`, transaction thứ hai không còn có thể tự mình `COMMIT` được nữa:

[source,console,role="transcript"]
....
-- session 2 (assume session 1 has issued COMMIT)
forumdb=> COMMIT;
ERROR:     could not serialize access due to read/write dependencies among
transactions
DETAIL: Reason code: Canceled on identification as a pivot, during commit
attempt.
HINT:     The transaction might succeed if retried.
....

.SQL
[source,sql]
....
-- session 2 (assume session 1 has issued COMMIT)
COMMIT;
....

.Output
[source,output]
....
ERROR:     could not serialize access due to read/write dependencies among
transactions
DETAIL: Reason code: Canceled on identification as a pivot, during commit
attempt.
HINT:     The transaction might succeed if retried.
....


Đây là một scenario khá phổ biến khi sử dụng transaction ở isolation level serializable: application hoặc user phải sẵn sàng retry transaction, vì PostgreSQL có thể khiến transaction đó thất bại do yêu cầu serializable của workflow.
