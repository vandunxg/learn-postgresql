= Configuration của cluster

PostgreSQL được cấu hình thông qua một nhóm text file chứa các directive và value dùng để bootstrap cluster và đưa cluster vào trạng thái hoạt động. Chúng ta đã thấy configuration file được xử lý như thế nào trong suốt cuốn sách, nhưng trong chapter này, chúng ta sẽ giải thích chi tiết cách quản lý configuration.

Có ba configuration file chính tạo thành *điểm bắt đầu* cho mọi configuration:

* `postgresql.conf` là file configuration chính của cluster, chứa toàn bộ data cần thiết để khởi động cluster, thiết lập process (chẳng hạn WAL sender) và logging, cũng như cấu hình cách cluster chấp nhận connection (ví dụ cluster sẽ lắng nghe trên TCP/IP address nào).
* `postgresql.auto.conf` là file được chính cluster tự động tạo và cập nhật, chứa các parameter mà superuser thay đổi từ bên trong cluster. Bạn không bao giờ nên edit file này thủ công, nhưng có thể kiểm tra file bằng text editor để đọc nội dung.
* `pg_hba.conf` là file dùng để cho phép hoặc từ chối client connection tới cluster. File này đã được giải thích rộng rãi trong Chapter 3, *Managing Users and Connections*, và liên quan đến cơ chế authentication của user và role.

Thông thường, ba file nói trên đều nằm trong directory `PGDATA`, nơi chứa toàn bộ data của cluster, nhưng một số operating system có thể đặt chúng trong directory khác; ví dụ, Debian GNU Linux thường đặt chúng trong `/etc/postgresql`.

[quote]
____
Trong các Docker image của cuốn sách, các configuration file được lưu trong directory `PGDATA`, cụ thể là `/postgres/16/data`.

____
Có những configuration file khác cũng thường được lưu trong directory `PGDATA`, nhưng chúng sẽ không được thảo luận ở đây. Section này chủ yếu tập trung vào `postgresql.conf`, configuration file mặc định.

File `postgresql.conf` là một text file, thường đi kèm các comment hữu ích, chứa một tập hợp configuration parameter. Mỗi parameter được biểu diễn dưới dạng `key = value`, trong đó key là tên configuration parameter và value là giá trị của parameter đó. Chúng ta đã thấy một số configuration parameter trong các chapter trước. Ví dụ, configuration parameter `max_wal_senders = 2` đặt parameter `max_wal_senders` thành 2.

Mỗi configuration parameter phải nằm trên một dòng riêng; mọi dòng bắt đầu bằng dấu `#` đều là comment và bị cluster bỏ qua. Comment hữu ích vì cho phép bạn ghi lại ý định đằng sau một configuration cụ thể. Ví dụ, hãy xem snippet sau:

[source,console,role="transcript"]
....
# set to 2 to allow pg_basebackup to work properly
max_wal_senders = 2
....

.Command
[source,bash]
....
set to 2 to allow pg_basebackup to work properly
....

.Output
[source,output]
....
max_wal_senders = 2
....


Ví dụ trên cho thấy rõ lý do parameter được cấu hình như vậy. Bạn không bắt buộc phải đặt comment trong configuration file, nhưng ghi lại thay đổi mình thực hiện và lý do của nó là một thói quen rất tốt.

Một parameter có thể được định nghĩa nhiều lần; khi đó, PostgreSQL sử dụng definition cuối cùng được tìm thấy.

Nếu không muốn cấu hình một parameter cụ thể, bạn có thể xóa dòng của parameter đó để nó biến mất hoàn toàn khỏi configuration file, hoặc đặt dấu comment phía trước để biến dòng đó thành một comment thuần túy. Điều quan trọng cần lưu ý là nếu một parameter không được cấu hình trong file vì bị thiếu hoặc đã bị comment out, nó sẽ nhận giá trị mặc định. Mọi parameter đều có giá trị mặc định, và bạn phải xem documentation để hiểu từng giá trị; tuy nhiên, configuration file mặc định của installation chứa tất cả parameter khả dụng cùng các comment giải thích cách sử dụng và thiết lập mặc định của chúng.

Mỗi configuration parameter chỉ chấp nhận một tập hợp giá trị cụ thể, tùy thuộc vào type của chính configuration parameter đó. Thông thường, bạn sẽ gặp giá trị số, chuỗi và list (phân tách bằng dấu phẩy); ngoài ra còn có giá trị đi kèm measurement unit, chẳng hạn thời gian như `2ms` (2 milliseconds), hoặc kích thước như `2GB` (2 gigabytes).

== Kiểm tra toàn bộ configuration parameter

Bạn có thể kiểm tra toàn bộ configuration parameter trên một system đang chạy bằng cách query catalog chuyên dụng `pg_settings`. Catalog này chứa mọi setting mà version PostgreSQL hiện tại chấp nhận, cùng default value, current value, mô tả mục đích của parameter và nhiều thông tin khác.

Ví dụ, query sau cho phép bạn thu thập thông tin về mọi configuration parameter, bao gồm short description và long description, default value và current value:

[source,console,role="transcript"]
....
forumdb=> SELECT name, setting || ' ' || unit AS current_value, short_
desc, extra_desc, min_val, max_val, boot_val, reset_val FROM pg_settings;
...
name           | authentication_timeout
current_value | 360 s
short_desc    | Sets the maximum allowed time to complete client
authentication.
extra_desc     |
min_val        | 1
max_val        | 600
boot_val       | 60
reset_val      | 360
....

.SQL
[source,sql]
....
SELECT
    name,
    setting || ' ' || unit AS current_value,
    short_ DESC,
    extra_desc,
    min_val,
    max_val,
    boot_val,
    reset_val
FROM pg_settings;
....

.Output
[source,output]
....
...
name           | authentication_timeout
current_value | 360 s
short_desc    | Sets the maximum allowed time to complete client
authentication.
extra_desc     |
min_val        | 1
max_val        | 600
boot_val       | 60
reset_val      | 360
....


Trong ví dụ trên, `authentication_timeout` được đặt thành 360 giây, như column `setting` cho thấy, và giá trị của nó có thể được điều chỉnh trong khoảng từ 1 giây đến 600 giây; `boot_val` là giá trị mặc định mà parameter sẽ nhận nếu hoàn toàn không được cấu hình, và được đặt thành 60 giây. Tương tự, column `reset_val` cho biết giá trị mà parameter sẽ nhận nếu được reset sau một thay đổi.

Catalog chuyên dụng `pg_settings` cũng chứa các thông tin hữu ích khác, bao gồm file và số dòng nơi parameter được load. Thông tin này có thể dùng để nhanh chóng tìm nơi một configuration parameter được đặt trong file `postgresql.conf` hoặc configuration file khác. Ví dụ, query sau cho biết từng parameter được load từ đâu:

[source,console,role="transcript"]
....
forumdb=# SELECT name, setting AS current_value, sourcefile, sourceline,
pending_restart FROM pg_settings;
...
name               | log_destination
current_value       | stderr
sourcefile          | /postgres/16/data/postgresql.auto.conf
sourceline          | 4
pending_restart | f
....

.SQL
[source,sql]
....
SELECT
    name,
    setting AS current_value,
    sourcefile,
    sourceline,
    pending_restart
FROM pg_settings;
....

.Output
[source,output]
....
...
name               | log_destination
current_value       | stderr
sourcefile          | /postgres/16/data/postgresql.auto.conf
sourceline          | 4
pending_restart | f
....


Như bạn có thể thấy trong ví dụ cài đặt này, configuration parameter `log_destination` đã được load từ file `/postgres/16/data/postgresql.auto.conf`. Đây không phải file `postgresql.conf` chính; đó là file được PostgreSQL tự động tạo để xử lý các configuration parameter được thay đổi từ bên trong cluster. Cách sử dụng `postgresql.auto.conf` sẽ trở nên rõ ràng hơn ở phần sau của chapter này; hiện tại, chỉ cần biết rằng configuration parameter này đã được load từ một file khác và `pg_settings` báo cáo rõ điều đó.

[quote]
____
Bạn cần quyền database superuser để lấy thông tin bổ sung, chẳng hạn vị trí file và số dòng.

____
Còn một thông tin quan trọng khác có thể lấy từ catalog chuyên dụng `pg_settings` là điều gì xảy ra khi một parameter được thay đổi tại runtime. Tùy vào bản chất của parameter, thay đổi có thể có hiệu lực ngay lập tức, bị trì hoãn trong khi chờ một event đặc biệt, hoặc thậm chí phải chờ cluster restart. Column `pending_restart` cho biết parameter hiện tại đã thay đổi so với boot-time value hay chưa, đồng thời thay đổi đó đã được áp dụng vào cluster hay chưa. Trong ví dụ trước, `pending_restart` là false, vì vậy configuration bạn đang thấy thực sự là configuration đang chạy trên cluster ngay lúc này.

Query `pg_settings` cung cấp mọi thông tin cần thiết để hiểu trạng thái của configuration hiện tại, nhưng có một cách nhanh hơn để lấy setting của parameter: command `SHOW`. Command đặc biệt `SHOW` nhận tên một parameter và trả về giá trị của parameter đó dưới dạng dễ đọc. Ví dụ, hãy tưởng tượng chúng ta muốn xem memory value `shared_buffers`:

[source,console,role="transcript"]
....
forumdb=> SHOW shared_buffers ;
shared_buffers
----------------
128MB
(1 row)
....

.SQL
[source,sql]
....
SHOW shared_buffers;
....

.Output
[source,output]
....
shared_buffers
----------------
128MB
(1 row)
....


Rõ ràng có thể lấy cùng thông tin từ `pg_settings`, nhưng phải dùng một query dài hơn và chuyển giá trị sang dạng dễ đọc (lưu ý rằng memory value được biểu diễn dưới dạng các chunk 8kB):

[source,console,role="transcript"]
....
forumdb=> SELECT name, setting, unit FROM pg_settings WHERE name =
'shared_buffers';
      name         | setting | unit
----------------+---------+------
shared_buffers | 16384        | 8kB
(1 row)
....

.SQL
[source,sql]
....
SELECT
    name,
    setting,
    unit
FROM pg_settings
WHERE name = 'shared_buffers';
....

.Output
[source,output]
....
      name         | setting | unit
----------------+---------+------
shared_buffers | 16384        | 8kB
(1 row)
....


Vì vậy, nếu chỉ cần xem nhanh một configuration parameter, `SHOW` là command phù hợp; còn nếu cần thông tin đầy đủ và chính xác hơn về giá trị, nơi parameter được đặt trong configuration file, v.v., bạn nên query catalog `pg_settings`.

== Tìm lỗi trong configuration

PostgreSQL cung cấp một catalog rất hữu ích tên là `pg_file_settings`, cho phép database administrator nhanh chóng xem tất cả configuration parameter, file được load và thông tin về các lỗi. Query sau đây trích xuất toàn bộ thông tin từ catalog; output được rút gọn dưới đây cung cấp một số thông tin quan trọng:

[source,console,role="transcript"]
....
postgres=# SELECT name, setting, sourcefile, sourceline, applied, error
FROM pg_file_settings where name = 'log_destination';
-[ RECORD 1 ]--------------------------------------
name          | log_destination
setting       | stderr
sourcefile | /postgres/16/data/postgresql.conf
sourceline | 444
applied       | f
error         |
-[ RECORD 2 ]--------------------------------------
name          | log_destination
setting       | csvlog
sourcefile | /postgres/16/data/postgresql.conf
sourceline | 818
applied       | f
error         |
-[ RECORD 3 ]--------------------------------------
name          | log_destination
setting       | stderr
sourcefile | /postgres/16/data/postgresql.auto.conf
sourceline | 4
applied       | t
error         |
....

.SQL
[source,sql]
....
SELECT
    name,
    setting,
    sourcefile,
    sourceline,
    applied,
    error

WHERE name = 'log_destination';
....

.Output
[source,output]
....
-[ RECORD 1 ]--------------------------------------

Như bạn có thể thấy trong ví dụ cài đặt trên, configuration parameter `log_destination` đã được load nhiều lần, chính xác là ba lần, từ các source file khác nhau. Configuration setting được áp dụng nằm trong file `/postgres/16/data/postgresql.auto.conf`, tại line 4, như trạng thái của column `applied` cho thấy. Nếu parameter có lỗi, column `error` sẽ cung cấp gợi ý về vấn đề.

Việc một parameter được định nghĩa nhiều lần trong cùng một file hoặc trong các file khác nhau không phải là lỗi, mà là cơ chế ghi đè parameter đó. View chuyên dụng `pg_file_settings` giúp bạn tìm hiểu tại sao một lần định nghĩa trong file chưa được load và những lần định nghĩa nào đã bị các lần định nghĩa khác ở nơi khác ghi đè.

Nếu một parameter không thể được áp dụng vì có lỗi, column `error` sẽ đưa ra gợi ý về vấn đề và column `applied` sẽ có giá trị false.

== Include các configuration file

Bạn không phải cấu hình mọi parameter bên trong file `postgresql.conf`: bạn có thể định nghĩa các configuration file nhỏ, tập trung theo từng mục đích, rồi yêu cầu PostgreSQL đọc và thêm nội dung của chúng vào configuration. Nhờ vậy, bạn có thể tạo một tập hợp configuration file nhỏ hơn và sạch hơn cho những tác vụ cụ thể, giúp việc maintenance đơn giản hơn.

PostgreSQL cung cấp ba directive chính để include các configuration file khác:

* `include_file`: include một file duy nhất trong configuration
* `include_dir`: include tất cả file nằm trong directory được chỉ định
* `include_if_exists`: chỉ include một file nếu file đó tồn tại

Directive include rất hữu ích vì nếu file được include không tồn tại, PostgreSQL sẽ báo lỗi; ngược lại, với `include_if_exists`, cluster sẽ không cảnh báo nếu file cần include chưa được tạo. Điều này hữu ích cho provisioning, chẳng hạn khi bạn có thể thiết lập một configuration file chính để include nhiều file rồi chỉ đưa những file đó vào các system thực sự cần configuration tương ứng.

Để xem một ví dụ cụ thể, giả sử có file tên `memory.conf` trong directory `PGDATA`, với nội dung như sau:

* `shared_buffers = 321 MB`
* `work_mem = 16 MB`

Sau đó thêm directive sau vào cuối file `postgresql.conf`:

[source,text]
....
include_if_exists = 'memory.conf'
....

Theo cách này, sau khi cluster restart, file `postgresql.conf` sẽ yêu cầu cluster load một configuration file khác có tên `memory.conf`; file này sẽ ghi đè một vài memory setting (hãy nhớ rằng definition cuối cùng của một configuration parameter là definition được chọn để áp dụng). Có thể xem kết quả cuối cùng bằng cách query catalog `pg_file_settings`:

[source,console,role="transcript"]
....
postgres=# SELECT * FROM pg_file_settings WHERE name IN ('shared_buffers',
'work_mem' );
             sourcefile                      | sourceline | seqno |              name        |
setting | applied | error
-----------------------------------+------------+-------+----------------
+---------+---------+-------
/postgres/16/data/postgresql.conf |                    127 |       3 | shared_buffers |
128MB   | f       |
/postgres/16/data/memory.conf              |             1 |      15 | shared_buffers |
321MB   | t       |
/postgres/16/data/memory.conf              |             2 |      16 | work_mem            |
16MB    | t       |
(3 rows)
....

.SQL
[source,sql]
....
SELECT *
FROM pg_file_settings
WHERE name IN ('shared_buffers', 'work_mem');
....

.Output
[source,output]
....
             sourcefile                      | sourceline | seqno |              name        |
setting | applied | error
-----------------------------------+------------+-------+----------------
+---------+---------+-------
/postgres/16/data/postgresql.conf |                    127 |       3 | shared_buffers |
128MB   | f       |
/postgres/16/data/memory.conf              |             1 |      15 | shared_buffers |
321MB   | t       |
/postgres/16/data/memory.conf              |             2 |      16 | work_mem            |
16MB    | t       |
(3 rows)
....


Như bạn có thể thấy, parameter `shared_buffers` đã bị ghi đè và được áp dụng từ file vừa tạo, còn `work_mem`, vốn được comment out trong default installation, cũng được áp dụng từ file được include mà không ghi đè bất kỳ definition nào khác.

== Các configuration context

Mỗi configuration parameter thuộc một context, tức một nhóm xác định thời điểm thay đổi đối với parameter đó có thể có hiệu lực. Một số parameter có thể được thay đổi và có hiệu lực trong suốt vòng đời của cluster. Tuy nhiên, một số parameter khác yêu cầu cluster restart; context của configuration parameter giúp system administrator hiểu khi nào các thay đổi sẽ có hiệu lực.

Có thể lấy configuration context từ catalog `pg_settings`, như trong ví dụ sau:

[source,console,role="transcript"]
....
forumdb=> SELECT distinct context FROM pg_settings ORDER BY context;
          context
-------------------
    backend
    internal
    postmaster
    sighup
    superuser
    superuser-backend
    user
(7 rows)
....

.SQL
[source,sql]
....
SELECT DISTINCT context
FROM pg_settings
ORDER BY context;
....

.Output
[source,output]
....
          context
-------------------
    backend
    internal
    postmaster
    sighup
    superuser
    superuser-backend
    user
(7 rows)
....


Như bạn có thể thấy, các configuration context hợp lệ gồm:

* `internal`: Giá trị configuration này phụ thuộc vào PostgreSQL source code và được thiết lập tại compile time, vì vậy không thể thay đổi trừ khi bạn quyết định compile lại từ đầu. Chẳng hạn, kích thước của mỗi memory page được định nghĩa trong source code.
* `postmaster`: Process này chịu trách nhiệm nhận các thay đổi. Nói cách khác, toàn bộ cluster (và main process của cluster, `postmaster`) phải được restart để thay đổi có hiệu lực.
* `sighup`: Với context này, cluster sẽ nhận các thay đổi khi nhận hang-up signal, thường thông qua một lần reload operating system service.
* superuser-backend và backend: Các thay đổi được áp dụng khi mở connection tiếp theo. Context `superuser-backend` cho phép superuser đặt giá trị, còn `backend` cho phép user đặt giá trị.
* `user` và `superuser`: Các thay đổi được áp dụng ngay lập tức cho connection hiện tại, bất kể đó là unprivileged connection hay connection từ superuser.

== Các configuration setting quan trọng

PostgreSQL có rất nhiều configuration option, và mô tả tất cả ở đây sẽ cần cả một cuốn sách. Hơn nữa, configuration phụ thuộc vào nhiều yếu tố khác nhau, bao gồm workload của cluster và connection concurrency. Nhiều parameter có thể làm thay đổi behavior của các parameter khác. Vì vậy, không thể đưa ra một hướng dẫn từng bước đơn giản mà vẫn hiệu quả cho configuration, nhưng có thể đưa ra một số gợi ý để giúp bạn bắt đầu tuning cluster.

Trong các subsection sau, bạn sẽ tìm hiểu về những configuration parameter chính theo category của chúng. Hãy dành thời gian hiểu rõ từng setting thực hiện điều gì trước khi áp dụng thay đổi, và nhớ rằng các configuration context có thể khiến bạn không thấy được kết quả ngay lập tức.

== Các setting về WAL

WAL giữ vai trò nền tảng để cluster hoạt động đúng và có thể recover sau crash. Vì vậy, các setting liên quan đến WAL có ý nghĩa sống còn trong vòng đời của cluster.

Các setting chính gồm:

* `fsync` yêu cầu cluster gọi system call `fsync(2)` mỗi khi thực hiện một `COMMIT`, tức là khi có data cần được lưu vào WAL segment.
* `wal_level` cho biết lượng thông tin mà cluster phải giữ trong WAL segment.
* `wal_sync_method` cho PostgreSQL biết nên dùng system call `fsync(2)` nào để đạt hiệu suất tốt.
* `synchronous_commit` cho PostgreSQL biết mỗi `COMMIT` có phải được theo sau ngay bởi một lần `fsync(2)` synchronous hay không, hoặc việc flush có thể được trì hoãn theo khoảng thời gian do `wal_writer_delay` xác định hay không.
* `wal_writer_delay` và `wal_writer_flush_after` xác định tần suất một process, được gọi là WAL writer, phải flush data xuống disk khi hoạt động ở asynchronous `COMMIT` mode. Sau khoảng thời gian tính bằng milliseconds tương ứng với `wal_writer_delay`, hoặc khi đã tích lũy số megabytes data tương ứng với `wal_writer_flush_after`, các asynchronous commit sẽ được flush xuống disk.
* `checkpoint_timeout`, `checkpoint_completion_target` và `max_wal_size` kiểm soát việc checkpoint, như đã thảo luận trong Chapter 11, Transactions, MVCC, WALs, and Checkpoints, khi chúng ta giải thích về transaction và WAL.

Setting fsync phải luôn được đặt thành `on`, vì tắt setting này sẽ khiến cluster có nguy cơ mất data: filesystem sẽ không flush data xuống disk tại thời điểm `COMMIT`, do đó PostgreSQL không đảm bảo data đã thực sự được lưu trên disk và, trong trường hợp crash (ví dụ mất điện), data có thể bị mất. Có rất ít scenario mà việc đặt option này thành `off` có ý nghĩa, nhưng hãy nhớ rằng nếu bạn thực sự tìm được một lý do như vậy, tắt option này vẫn khiến cluster của bạn không thể tồn tại sau crash.

Setting `wal_level` cho biết lượng thông tin PostgreSQL phải tích lũy trong WAL segment. Mục đích chính của WAL là giúp cluster có thể tồn tại sau crash, nhưng WAL cũng được dùng để truyền thay đổi sang các cluster khác trong replication scenario.

Setting `wal_level` có thể được đặt thành `minimal`, tức một cluster đơn lẻ với toàn bộ thông tin cần thiết để tồn tại sau crash; hoặc `replica` (default), khiến WAL cũng hữu ích cho các physical replication scenario; và cuối cùng có thể chuyển thành `logical`, khiến WAL chứa thông tin cho cả các logical replication scenario.

`wal_sync_method` cho phép administrator cấu hình một operating system call cụ thể để sync dirty buffer. Tất cả POSIX operating system đều implement `fsync(2)`, nhưng một số system cung cấp các biến thể đặc biệt hoạt động nhanh hơn hoặc tốt hơn tùy thuộc vào filesystem. Có thể chỉ định chính xác tên của system call cần dùng thông qua `wal_sync_method`. Thông thường, PostgreSQL đi kèm configuration phù hợp cho operating system.

`synchronous_commit` là một parameter có nhiều lựa chọn, cho biết cần ghi bao nhiêu WAL xuống disk trước khi trả về trạng thái “success” cho transaction thực hiện `COMMIT`. Theo mặc định, setting này có giá trị `on`, nghĩa là mọi phần WAL cần thiết phải được ghi xuống disk trước khi transaction được phép thành công.

Đặt parameter thành `off` có nghĩa transaction sẽ thành công ngay cả khi WAL chưa được flush xuống disk. Không giống setting `fsync`, việc chuyển `synchronous_commit` thành `off` là an toàn và không gây mất data, vì asynchronous commit được điều khiển bởi `wal_writer_delay`, nghĩa là transaction sẽ được consolidate ở thời điểm muộn hơn. Ngoài ra còn có các giá trị khác cho parameter này, tất cả đều hàm ý behavior `on`: `local`, `remote_apply` và `remote_write`. Các setting này chỉ có ý nghĩa trong replication scenario khi cluster này hoạt động như một primary và được một (hoặc nhiều) standby cluster theo sau. Trong scenario này, `local` có nghĩa transaction sẽ thành công ngay khi primary đã flush từng phần WAL xuống disk (tức behavior `on` mặc định); ngược lại, `remote_write` sẽ chờ các standby xác nhận rằng chúng đã nhận WAL tương ứng và sắp replicate nó, nghĩa là primary đã consolidate transaction và standby sẽ sớm làm điều tương tự. Cuối cùng, `remote_write` sẽ chờ transaction thành công cho đến khi cả primary và standby đã flush toàn bộ data xuống disk.

== Các setting liên quan đến memory

PostgreSQL tận dụng volatile RAM của system để cache data từ permanent storage và quản lý việc lưu data lâu dài.

Các setting chính liên quan đến memory management gồm:

* `shared_buffers` là lượng memory PostgreSQL sẽ dùng để cache data trong memory.
* `work_mem` là lượng memory PostgreSQL sẽ cung cấp theo nhu cầu để thực hiện các activity cụ thể trên data.
* `hash_mem_multiplier` được dùng để xác định một ngưỡng về lượng memory mà một connection có thể dùng cho các hash-based operation.
* `maintenance_work_mem` là lượng memory PostgreSQL dành riêng cho các operation nội bộ.
* `wal_buffers` là cache được dùng cho WAL segment.

`shared_buffers` có lẽ là setting quan trọng nhất ở đây vì nó xác định tổng lượng memory PostgreSQL sẽ dùng. Memory này được dành riêng cho PostgreSQL và các process do PostgreSQL spawn; các service khác đang chạy trên cùng machine sẽ không thể dùng memory đó. Thông thường, bạn nên bắt đầu với một giá trị nằm trong khoảng 25% đến 45% tổng RAM của system. Giá trị quá thấp sẽ khiến PostgreSQL phải load data từ permanent storage rồi flush data trở lại permanent storage, còn giá trị quá cao sẽ khiến PostgreSQL cạnh tranh với filesystem cache của operating system, từ đó có thể gây ra performance issue.

`work_mem` là lượng memory mà mỗi connection có thể dùng để thực hiện một hoạt động sắp xếp lại data cụ thể, chẳng hạn như hoạt động trong một `SORT` hoặc một hash join. Khi xử lý các hash-based task, một connection được phép dùng lượng memory bằng `work_mem * hash_mem_multiplier` trước khi process chuyển sang swap trên disk. Trong mọi trường hợp, khi process không còn cách nào dùng thêm memory, nó sẽ bắt đầu swap xuống disk, chẳng hạn chuyển một in-memory `SORT` thành một on-disk merge `SORT`.

`maintanance_work_mem` thiết lập lượng memory trên mỗi session dành cho các command chuyên sâu như `VACUUM` và `CREATE INDEX`. Vì mỗi connection chỉ có thể thực hiện một trong các command đó tại một thời điểm, bạn có thể tăng giá trị tùy theo số administrative connection mà bạn dự kiến sẽ phục vụ.

`wal_buffers` có lẽ là setting dễ tune nhất liên quan đến memory: nó cho biết cần dùng bao nhiêu memory để cache WAL segment. Vì WAL segment thường được write thành các chunk 16 megabytes, đây chính xác là giá trị tối ưu cho setting này.

== Các setting liên quan đến process

PostgreSQL là một multi-process system và spawn một process để phục vụ mỗi connection đến. Một vài setting có thể hỗ trợ theo dõi từng process liên quan đến PostgreSQL từ góc nhìn của operating system:

* `update_process_title` khiến mỗi process báo cáo công việc nó đang làm; ví dụ query mà nó đang thực thi khi được các operating system tool như `ps(1)` và `top(1)` yêu cầu.
* `cluster_name` là một tên gợi nhớ dùng để nhận diện cluster mà mỗi process thuộc về trong trường hợp có nhiều cluster đang chạy trên cùng machine.

Cần lưu ý rằng các setting này có thể làm system hoạt động chậm hơn trên một số operating system nhất định, chẳng hạn như FreeBSD.

Các log-related setting đã được giải thích chi tiết trong Chapter 14, Logging and Auditing, vì vậy sẽ không được thảo luận lại ở đây.

== Các setting liên quan đến network

Thông thường, PostgreSQL lắng nghe trên một TCP/IP address cho các connection đến; address này được chỉ định bởi một nhóm setting liên quan đến network. Các setting chính cho việc này gồm:

* `listen_addresses` chỉ định các TCP/IP address cần lắng nghe.
* `port` chỉ định TCP/IP port mà `postmaster` sẽ chờ connection đến.
* `max_connections`, `reserved_connections` và `superuser_reserved_connections` chỉ định số connection đến được phép.
* `authentication_timeout` và `ssl` cho biết authentication timeout và chế độ mã hóa.

`listen_addresses` có thể chứa nhiều address, được phân tách bằng dấu phẩy, khi server là multi-homed. Nó thậm chí có thể được chỉ định bằng giá trị đặc biệt `*` để cho biết server phải lắng nghe trên mọi address khả dụng. `port` chỉ định số TCP/IP port, mặc định là 5432.

`max_connections` là giới hạn tối đa cho connection đến: khi đạt ngưỡng này, cluster sẽ không cho phép thêm connection nào. Một số slot được dành cho superuser theo `superuser_reserved_connection`, để trong tình huống khẩn cấp superuser vẫn có thể kết nối tới cluster. Cuối cùng, `reserved_connections` đếm số connection được thiết lập bởi user có role đặc biệt `pg_use_reserved_connection`, đồng thời cho biết một tập user đặc biệt (không phải superuser) có các reserved connection slot. Vì vậy, số connection còn trống mà một user thông thường có thể sử dụng là `max_connections – superuser_reserved_connection – reserved_connections`.

`authentication_timeout` là khoảng thời gian trước khi một lần thử authentication hết hạn, còn `ssl` cho phép server xử lý SSL handshake trên connection (SSL sẽ không được giải thích ở đây).

____
Có rất nhiều parameter để tinh chỉnh SSL và giai đoạn authentication không được đề cập trong cuốn sách này vì chúng cũng yêu cầu nền tảng chuyên sâu về các chủ đề đó.

== Các setting về archiving và replication

Có nhiều setting về archiving và replication liên quan đến cách cluster archive WAL và giao tiếp với các cluster khác với tư cách primary hoặc standby. Tất cả setting sẽ được trình bày chi tiết trong Chapter 17, Physical Replication, và Chapter 18, Logical Replication; ở đây chúng chỉ được liệt kê sơ lược:

* `wal_level` (đã được thảo luận trong section trước) cho biết thông tin trong WAL sẽ được sử dụng như thế nào. Nó có thể là `minimal` (đối với standalone system), `replica` (đối với replicated system), hoặc `logical` (đối với logical replication).
* `archive_mode`, `archive_command`, `archive_library` và `archive_timeout` quản lý archiving mode, tức lưu WAL tới các vị trí khác để point-in-time recovery hoặc replication.
* `primary_conninfo` và `primary_slot_name` được dùng để xác định connection từ standby node tới primary node.
* `hot_standby`, khi được dùng trên một replicating system, cho phép thực hiện read-only query.
* `max_standby_archive_delay` và `max_standby_streaming_delay` xác định khoảng thời gian trước khi một conflicting query trên standby phải bị hủy do một hành động khác đã xảy ra trên primary.
* `recovery_min_apply_delay` tạo độ trễ trên standby node để nó có thể theo primary với một độ lệch thời gian.
* `max_replication_slots` và `max_wal_senders` được dùng để xác định số replication slot sẽ được chấp nhận và sử dụng, cũng như số process sẽ quản lý replication.
* `synchronous_standby_names` xác định node nào được xem là synchronous trong replication, và vì vậy primary phải nhận feedback liên tục trước khi commit các thay đổi.

Các setting này và những setting khác liên quan đến replication sẽ được thảo luận trong Chapter 17, Physical Replication, và Chapter 18, Logical Replication.

== Các setting liên quan đến vacuum và autovacuum

Có nhiều setting có thể dùng để xác định và điều chỉnh vacuum cũng như autovacuum. Những setting này đã được thảo luận trong Chapter 11, Transactions, MVCC, WALs, and Checkpoints.

== Các setting của optimizer

PostgreSQL optimizer sử dụng cost-based approach. Bạn có thể điều chỉnh các cost này, như đã thảo luận trong Chapter 13, Query Tuning, Indexes, and Performance Optimization.

== Statistics collector

PostgreSQL sử dụng statistics collector để thu thập thông tin về những gì đã xảy ra trong cluster, như bạn sẽ tìm hiểu sau trong chapter này, ở section Theo dõi cluster.

Vì việc thu thập các số liệu đó có rất ít runtime impact, bạn có thể loại bỏ hoàn toàn việc thu thập hoặc lọc thông tin mà statistics collector thu thập để chỉ giữ lại những gì mình thực sự quan tâm. Các setting chính cho việc này gồm:

* `track_activities` cho phép các process khác theo dõi command hoặc query hiện đang được thực thi.
* `track_counts` thu thập thông tin đếm về table và việc sử dụng index.
* `track_functions` thu thập statistics về việc sử dụng các function và stored procedure.
* `track_io_timing` cho phép chúng ta đo thời gian đã dùng trong các thao tác input/output khác nhau.
* `stat_temp_directory` là tên directory (relative) được dùng làm storage tạm thời cho việc thu thập statistics.

== Thay đổi configuration trên system đang chạy

Bạn có thể thay đổi configuration của cluster từ bên trong database connection bằng command `ALTER SYSTEM`.

`ALTER SYSTEM` cung cấp một cách thức SQL để đặt giá trị của parameter; parameter đó sẽ được thêm vào file đặc biệt `postgresql.auto.conf`, nằm trong directory `PGDATA`. File `postgresql.auto.conf` được tự động load ở cuối khi server start hoặc khi có reload signal (`HUP`) được phát ra. Vì vậy, các parameter nằm trong `postgresql.auto.conf` sẽ được ưu tiên hơn các parameter trong `postgresql.conf`, và các thay đổi sẽ được áp dụng như thể bạn đã tự chỉnh sửa file `postgresql.conf`.

Chỉ database administrator mới có thể thực thi `ALTER SYSTEM`. Ví dụ, giả sử bạn thực thi command sau:

[source,console,role="transcript"]
....
forumdb=# ALTER SYSTEM SET archive_mode = 'on';
ALTER SYSTEM
....

.SQL
[source,sql]
....
ALTER SYSTEM SET archive_mode = 'on';
....

.Output
[source,output]
....
ALTER SYSTEM
....


Kết quả cuối cùng sẽ là một file `postgresql.auto.conf` có nội dung như sau:

[source,console,role="transcript"]
....
$ cat /postgres/16/data/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
archive_mode = 'on'
....

.Command
[source,bash]
....

....

[source,output]

Như bạn thấy, parameter đã thay đổi được ghi vào file giống như khi bạn tự chỉnh sửa file đó. File chứa một banner cảnh báo rằng không nên tự chỉnh sửa, vì system sẽ không tính đến các thay đổi của bạn và sẽ ghi đè nội dung file.

Cũng có thể chỉ định `DEFAULT` làm giá trị cho một option; khi đó option này sẽ bị xóa khỏi file `postgresql.conf.auto`. `ALTER SYSTEM` cũng hỗ trợ `RESET` để reset một setting về giá trị trước đó, hoặc `RESET ALL` để reset toàn bộ setting từ `postgresql.auto.conf`.

Giả sử chúng ta chỉ thay đổi `archive_mode` như trong ví dụ trước, hai command sau tương đương và sẽ xóa các setting đã thay đổi khỏi file `postgresql.auto.conf`:

== Các tool tạo configuration

Thay vì bắt đầu từ file `postgresql.conf` có sẵn comment rồi tự tuning, bạn có thể tận dụng một hệ thống tuning tự động để tạo configuration từ đầu. Configuration như vậy có thể đủ tốt, hoặc ít nhất là điểm bắt đầu cho các cải tiến tiếp theo, tùy theo nhu cầu của bạn và chất lượng của tool đã tạo ra configuration đó.

Một tool tạo configuration tốt là *PGConfig*, một tool online có tại `https://www.pgconfig.org`, nơi bạn có thể chỉ định các setting chính của host phục vụ cluster, chẳng hạn như memory, loại hard disk, concurrency, v.v.

*Hình 16.1: PGConfig, tool tự động tạo configuration cho PostgreSQL*

Tool cho phép bạn chọn nhiều preset configuration, chẳng hạn như On-Line Transactional Processing (OLTP), On-Line Analytical Processing (OLAP), hoặc thậm chí một web application.

Sau khi chọn configuration phù hợp nhất với workload, bạn có thể xuất configuration đó thành một file `postgresql.conf` hoặc thành một tập hợp `ALTER SYSTEM` statement để thực thi dưới dạng SQL interactive script, nhờ đó bạn có thể áp dụng configuration cho cluster:

image::chapter-16-figure-16-2.jpg[Hình 16.2: Ví dụ về configuration được tự động tạo]

*Hình 16.2: Ví dụ về configuration được tự động tạo*

Như bạn thấy, kết quả là một loạt configuration parameter mà bạn có thể sao chép vào một configuration file “trống”. Ý tưởng là bắt đầu từ configuration này rồi tiếp tục tuning trên nền tảng đó.

Ảnh chụp màn hình sau hiển thị chính configuration đó nhưng được tạo bằng các `ALTER SYSTEM` statement; nghĩa là, tùy theo nhu cầu, bạn có thể áp dụng configuration dưới dạng một SQL script:

image::chapter-16-figure-16-3.jpg[Hình 16.3: Ví dụ về configuration được tự động tạo dựa trên các `ALTER SYSTEM` command]

*Hình 16.3: Ví dụ về configuration được tự động tạo dựa trên các `ALTER SYSTEM` command*

PGConfig chỉ là một option bạn có thể dùng để lấy một configuration tùy chỉnh làm điểm bắt đầu. Tất nhiên, bạn không bắt buộc phải dùng nó vì PostgreSQL đi kèm một configuration mặc định, và tool này không phải là một “giải pháp vạn năng” cung cấp configuration tối ưu cho cluster của bạn. Trong mọi trường hợp, bạn vẫn cần tuning và điều chỉnh các parameter để tối ưu cluster, tùy thuộc vào nhu cầu, workload và phần cứng của bạn.

Trong section tiếp theo, bạn sẽ tìm hiểu cách theo dõi cluster, cũng như cách phát hiện bottleneck và vấn đề có thể được khắc phục bằng cách tuning query hoặc configuration của cluster.
