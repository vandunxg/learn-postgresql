- `track_functions` thu thập statistics về việc sử dụng các function và stored procedure.
- `track_io_timing` cho phép chúng ta đếm thời gian đã dùng trong các thao tác input/output khác nhau.
- `stat_temp_directory` là tên directory (relative) được dùng làm storage tạm thời cho việc thu thập statistics.

## Thay đổi configuration từ một system đang hoạt động

Có thể thay đổi cluster configuration từ bên trong một database connection bằng command `ALTER SYSTEM`.

`ALTER SYSTEM` cung cấp cho chúng ta một cách thức SQL để thiết lập giá trị parameter; parameter đó sẽ được thêm vào file đặc biệt `postgresql.auto.conf`, nằm trong directory `PGDATA`. File `postgresql.auto.conf` được tự động load ở cuối, khi server khởi động hoặc khi có một reload signal (`HUP`) được phát ra. Do đó, các parameter nằm trong `postgresql.auto.conf` sẽ được ưu tiên hơn các parameter trong `postgresql.conf`, và kết quả là các thay đổi sẽ được áp dụng như thể bạn đã tự chỉnh sửa file `postgresql.conf`.

Chỉ database administrator mới có thể thực thi `ALTER SYSTEM`. Ví dụ, giả sử bạn phát hành command sau:


```text
forumdb=# ALTER SYSTEM SET archive_mode = 'on';
ALTER SYSTEM
```

Kết quả cuối cùng sẽ là một file `postgresql.auto.conf` có nội dung như sau:

```text
$ cat /postgres/16/data/postgresql.auto.conf
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
archive_mode = 'on'
```

Như bạn thấy, parameter đã thay đổi được đặt vào file giống như khi bạn tự chỉnh sửa file đó. File chứa một warning banner về việc không nên tự chỉnh sửa, vì system sẽ không tính đến các thay đổi của bạn và sẽ ghi đè nội dung của file.

Cũng có thể chỉ định `DEFAULT` làm giá trị cho một option, khi đó option này sẽ bị xóa khỏi file `postgresql.conf.auto`. `ALTER SYSTEM` cũng hỗ trợ `RESET` để reset một setting về giá trị trước đó, hoặc `RESET ALL` để reset toàn bộ setting từ `postgresql.auto.conf`.

Giả sử chúng ta chỉ thay đổi `archive_mode` như trong ví dụ trước, hai command sau tương đương và dẫn đến việc xóa các setting đã thay đổi khỏi file `postgresql.auto.conf`:

```text
forumdb=# ALTER SYSTEM SET archive_mode TO DEFAULT;
ALTER SYSTEM
forumdb=# ALTER SYSTEM RESET archive_mode;
ALTER SYSTEM
```

Input sau sẽ xóa mọi setting đã thay đổi trong `postgresql.auto.conf`:

```text
forumdb=# ALTER SYSTEM RESET ALL;
ALTER SYSTEM
```

Những configuration như vậy có thể đã đủ tốt, hoặc ít nhất là một điểm bắt đầu cho các cải tiến tiếp theo, tùy theo nhu cầu của bạn và mức độ tốt của tool đã tạo ra configuration đó.

## Monitoring the cluster

Monitoring cluster cho phép bạn hiểu cluster đang làm gì tại bất kỳ thời điểm nào, và có khả năng hành động cũng như phản ứng phù hợp để tránh suy giảm performance và usability của database. PostgreSQL cung cấp một tập catalog phong phú, cho phép database administrator monitor toàn bộ activity chỉ bằng cách phát hành các SQL statement và query.

Bạn cũng có thể kết hợp kết quả thông tin lấy từ catalog với các monitoring tool bên ngoài khác, từ tool của operating system đến những tool phức tạp hơn như Nagios.

Trong section này, chúng ta sẽ xem xét các PostgreSQL catalog chính được dùng để monitor và thu thập thông tin về database activity. Như bạn có thể hình dung, chỉ database administrator mới có thể lấy được thông tin đầy đủ về activity của toàn cluster.

Cluster thu thập thông tin về activity thông qua **statistic collector**, một process chuyên trách việc thu thập và do đó cung cấp thông tin trên phạm vi toàn cluster. Statistics không phải là realtime, dù bạn có cảm giác như vậy. Đó là vì backend process cập nhật statistics không thường xuyên hơn một lần mỗi 500 milliseconds, với điều kiện chúng đang idle. Hơn nữa, statistics bên trong một transaction block bị “frozen”, nghĩa là bạn không thể quan sát các thay đổi trong statistics cho đến khi transaction của bạn kết thúc.

Statistics được giữ lại qua các lần shutdown và restart sạch của cluster, nhưng trong trường hợp recovery từ một crash, toàn bộ statistics sẽ bị xóa và việc thu thập bắt đầu lại từ đầu. Cũng có thể reset thủ công statistics cho một database cụ thể bằng cách gọi function `pg_stat_reset()` với tư cách database superuser.

Trong các subsection sau, chúng ta sẽ tập trung vào một tập statistics có thể hữu ích để hiểu điều gì đang diễn ra bên trong cluster, qua đó hỗ trợ monitor toàn bộ activity.

### Information about running queries and sessions

Catalog `pg_stat_activity` cung cấp một tuple cho mỗi backend process đang active trong cluster và do đó cho mỗi client đang connected. Các query đơn giản sau cung cấp output chi tiết:

```text
forumdb=# SELECT usename, datname, client_addr, application_name,
             backend_start, query_start,
             state, backend_xid, query
    FROM pg_stat_activity;
...
-[ RECORD 4 ]----+--------------------------------------------------------
----------------------
usename               | luca
datname               | forumdb
client_addr           | 192.168.222.1
application_name | psql
backend_start        | 2023-09-13 16:42:50.9931+02
query_start          | 2023-09-13 16:44:20.601118+02
state                | idle
backend_xid          |
query            | INSERT INTO tags( tag ) SELECT 'A Fake Tag' FROM
generate_series( 1, 10000 );
```

Như bạn thấy, user `luca` (trong field `usename`) được connected thông qua `psql` (field `application_name`) từ một host remote (field `client_addr`) và đã thực thi query `INSERT INTO` trên table `tags` trong database `forumdb`. Điều đáng chú ý là field `state`, field báo cáo status của query đang chạy. Trong ví dụ trước, giá trị là `idle`, nghĩa là query đang chờ một việc khác xảy ra, và thậm chí có thể đã hoàn tất.

Cần lưu ý rằng catalog `pg_stat_activity` chỉ báo cáo query được thực thi gần nhất từ một session hoặc connection. Hãy nhớ rằng catalog hiển thị một tuple cho mỗi client đang connected và statistics không được cập nhật cho đến khi một statement mới được thực thi.

Catalog `pg_stat_activity` có thể được query bởi bất kỳ ai, kể cả user thông thường, nhưng lượng thông tin được báo cáo có thể bị cắt giảm tùy theo privilege của user thực thi query.

### Inspecting locks

Special catalog `pg_locks` cung cấp một view rõ ràng và chi tiết về mọi lock được các transaction và statement khác nhau acquire. Ý tưởng là bằng cách inspect catalog này, system administrator có thể nhanh chóng thấy các bottleneck tiềm ẩn và sự cạnh tranh giữa các transaction. Việc query catalog này bằng cách join nó với `pg_stat_activity` rất hữu ích để có thêm thông tin chi tiết về những gì đang diễn ra. Sau đây là một ví dụ về query và một phần result:

```text
forumdb=# SELECT a.usename, a.application_name, a.datname, a.query,
           l.granted, l.mode
      FROM pg_locks l
      JOIN pg_stat_activity a ON a.pid = l.pid;
...
-[ RECORD 5 ]----+--------------------------------------------------------
--
usename              | luca
application_name | psql
datname              | forumdb
query                | delete from tags;
granted              | t
mode                 | RowExclusiveLock
...
-[ RECORD 9 ]----+--------------------------------------------------------
--
usename              | luca
application_name | psql
datname              | forumdb
query                | insert into tags( tag ) values( 'FreeBSD' );
granted              | t
mode                 | ExclusiveLock
```

Có hai connection của user `luca` tới database `forumdb`, và một connection đã acquire lock để xóa tuple trong khi connection còn lại đang insert tuple vào table `tags`. Column `granted` cho biết lock đã được acquire hay chưa, vì vậy việc chỉ chọn các lock non-granted là một điểm khởi đầu tốt để tìm hiểu về các query bị block. Column `mode` cho biết loại lock mà query đang cố acquire.

Với các gợi ý này, và một lần nữa nhờ join chính xác với `pg_stat_activity`, bạn có thể tìm các query bị block, như trong ví dụ sau (đây là phần tiếp theo của cùng scenario đã mô tả trước đó):

```text
forumdb=# SELECT query, backend_start, xact_start, query_start,
           state_change, state,
           now()::time - state_change::time AS locked_since,
           pid, wait_event_type, wait_event
    FROM pg_stat_activity
    WHERE wait_event_type IS NOT NULL
    ORDER BY locked_since DESC;
...
-[ RECORD 6 ]---+---------------------------------------------
query               | insert into tags( tag ) values( 'FreeBSD' );
backend_start       | 2023-09-14 08:26:57.762887+02
xact_start          | 2023-09-14 08:27:00.017983+02
query_start         | 2023-09-14 08:27:14.745784+02
state_change        | 2023-09-14 08:27:14.775535+02
state               | idle in transaction
locked_since        | 00:07:33.411832
pid                 | 60239
wait_event_type | Client
wait_event          | ClientRead
```

Như bạn thấy, query đã chờ 7 phút 33 giây (column `locked_since`), nhưng query đang ở trạng thái `idle in transaction` (column `state`) và đang chờ input từ một client (các column `wait_event` và `wait_event_type`). Nói cách khác, query đang chờ user hoàn tất transaction (bằng `COMMIT` hoặc `ROLLBACK`).

Tận dụng `pg_locks` có thể giúp bạn theo dõi diễn tiến của transaction và sự tranh chấp giữa chúng, cũng như quyết định cách terminate các query đang block workload khác.

Cũng có một utility function tên là `pg_blocking_pids()` nhận process identifier của một backend và trả về danh sách process identifier đang block process đó.

### Inspecting databases

Bạn có thể lấy thông tin chi tiết về status của các database bằng cách query special catalog `pg_stat_database`. Catalog này cung cấp thông tin về các transaction `COMMIT` và `ROLLBACK`, deadlock và conflict. Hãy lưu ý rằng deadlock và rollback là các event tự nhiên trong một database, nhưng nếu bạn thấy các con số tăng nhanh, điều đó có thể nghĩa là đã xảy ra lỗi trong application hoặc có client đang cố thực hiện sai trong database và do đó buộc phải rollback.

Ví dụ, bằng cách sử dụng query sau, bạn có thể lấy thông tin chi tiết về các database của mình:

```text
forumdb=# SELECT datname, xact_commit, xact_rollback, blks_read,
conflicts, deadlocks,
           tup_fetched, tup_inserted, tup_updated, tup_deleted, stats_reset
           FROM pg_stat_database;
...
-[ RECORD 6 ]-+------------------------------
datname         | forumdb
xact_commit    | 802
xact_rollback | 9
blks_read      | 1800
conflicts      | 0
deadlocks      | 0
tup_fetched    | 32977
tup_inserted     | 1391
tup_updated      | 46
tup_deleted      | 0
stats_reset      |
```

Như bạn thấy, database `forumdb` không có conflict hoặc deadlock nào, và số transaction đã commit (column `xact_commit`) cao hơn nhiều so với số transaction đã abort (column `xact_rollback`). Vì vậy, chúng ta có thể giả định rằng database đang ổn và application đang phát hành các query tốt.

Column cuối cùng, `stats_reset`, đặc biệt quan trọng vì nó cho biết statistics information của một database đã được reset, tức là đã bị xóa, hay chưa. Biết đã bao lâu kể từ khi statistics được reset sẽ giúp xác thực database. Nếu column này rỗng, statistics của database chưa bao giờ được reset thủ công.

### Inspecting tables and indexes

Các special catalog `pg_stat_user_tables` và `pg_stat_user_indexes` cung cấp thông tin chi tiết về việc sử dụng một table hoặc một index, chẳng hạn như số tuple, số lần đọc và ghi, v.v.

Để hiểu rõ hơn, hãy xét một table trong đó một số transaction đã bị xóa hoặc cập nhật và các record mới được insert; query sau cung cấp thông tin chi tiết về status của table đó:

```text
forumdb=# SELECT relname, seq_scan, idx_scan,
             n_tup_ins, n_tup_del, n_tup_upd, n_tup_hot_upd,
             n_live_tup, n_dead_tup,
             last_vacuum, last_autovacuum,
             last_analyze, last_autoanalyze
             FROM pg_stat_user_tables;


-[ RECORD 1 ]----+------------------------------
relname              | tags
seq_scan             | 20
idx_scan             | 0
n_tup_ins            | 100007
n_tup_del            | 63
```
